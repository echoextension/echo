# ECHO 知乎与 B 站功能独立来源审计记录

> 审计类型：独立源码来源与第三方代码引入审查
> 审计日期：2026-09-05
> 审计对象：ECHO 浏览器扩展中知乎黑名单与 B 站推荐批次回退功能
> 审计基线：当前工作区 `feature/zhihu-blocklist-bili-feed-history` 分支，版本 `1.4.3`
> 文档性质：长期工程留档与来源审计记录，不构成法律意见

## 结论摘要

本次对知乎黑名单和 B 站推荐批次回退功能进行了一轮独立的来源审查。审查同时覆盖了历史调研材料、外部参考项目、ECHO 生产源码、依赖清单、许可证文件、Git 历史和全仓库标识反查。

在本次审查能够取得和复核的证据范围内：

1. 未发现 ECHO 生产代码直接复制外部仓库源码的证据。
2. 未发现目标外部项目被作为运行时依赖、打包输入或源码导入进入 ECHO。
3. 未发现外部项目的作者标识、许可证头、专属命名空间、整段函数表达、成套 CSS、专属 DOM 标识或外部 UI 文案进入 ECHO 生产实现。
4. ECHO 的两个功能在数据模型、模块边界、状态管理、通信方式、DOM 处理方式和渲染策略上均表现为独立实现。
5. 综合现有证据，AI 在实现过程中暗中复制第三方生产源码的可能性判断为**极低**，当前没有事实依据认定存在第三方源码引入或实质性代码复制。
6. 基于本次审查结果，当前没有必要为这两个功能新增第三方代码版权归属或第三方许可证声明。

上述结论不是“百分之百证明从未接触过任何外部源码”。静态仓库审计无法重建所有历史模型上下文，也无法从代码结果反向证明某个 AI 在物理意义上从未读取过某个公开页面。因此，本记录同时保留这一边界：**我们不能绝对排除未留存的历史访问或未进入当前工作区的参考过程，但已经对最终代码和可追溯工程材料进行了尽可能具体的独立核查，现有结果支持独立实现结论。**

## 一、审查主体与独立性说明

### 1.1 审查主体

本记录由当前审查 agent 在 2026-09-05 形成。根据本次协作上下文：

- 当前审查 agent 与此前负责实现功能的代码 agent 不是同一个 agent。
- 当前审查 agent 没有参与知乎黑名单和 B 站推荐批次回退功能的代码撰写。
- 当前审查过程中没有修改上述功能的生产源码；审查行为是读取、比对、搜索和验证。
- 当前审查 agent 以已有工作区、Git 历史、调研材料和固定外部提交为证据进行复核，而不是接受“代码是独立实现”的口头前提后直接确认。

这里的“独立”是工程审查意义上的独立：审查主体与实现主体分离，并对实现结果重新取证。它不是对所有历史模型上下文、未保存的浏览记录或任何 AI 内部运行状态的绝对证明。

### 1.2 独立性边界

本审查不能证明以下事项：

- 不能证明所有历史 AI 会话中从未打开、读取或参考过外部仓库源码。
- 不能证明所有未保存的中间草稿、模型上下文或外部工具返回结果都曾进入本次审查范围。
- 不能用“当前仓库没有第三方文件”单独证明历史上绝无第三方代码片段曾被尝试过。
- 不能替代版权所有者、律师或发行平台对具体法律问题的正式意见。

但这些边界不削弱本次工程结论的实际意义：代码复制风险最终需要在可交付产物中留下可识别的表达、结构、命名、依赖、许可证痕迹或历史引入路径；本次审查针对这些可检查对象进行了系统核对，未发现相应证据。

## 三、审查方法

本次审查采用“来源材料复核 + 生产实现对照 + 引入链检查 + 专属表达反查”的组合方法，而不是只检查依赖清单或只比较功能名称。

### 3.1 读取历史调研和许可证分析

首先读取 ECHO 已有的知乎/B站调研文档，确认：

- 当初为什么需要这两个功能。
- 调研时具体查看了哪些外部项目。
- 外部项目使用了哪些数据模型、函数组织、DOM 选择器和存储方式。
- 每个外部项目的许可证或无许可证状态是什么。
- 调研文档是否已经明确禁止复制源码、函数结构、变量命名、成套 CSS、文案、图标和页面布局。
- ECHO 当时是否把“参考产品思路”与“可直接复用代码”区分开。

复核结果是：调研材料明确区分了需求、公开行为、技术可行性和受版权保护的具体代码表达；对于两个无许可证的 B 站项目，文档明确采用“只研究、不复制”的策略。

### 3.2 对照 ECHO 生产实现

对生产源码进行逐模块阅读和搜索，重点检查：

- 函数和变量命名。
- 数据结构和序列化格式。
- 状态机和生命周期。
- DOM 选择器及其组合方式。
- 存储键、消息名、CSS 类名、元素 ID。
- 动态页面监听方式。
- 卡片提取、作者识别、历史恢复和过滤流程。
- 是否存在整段外部函数、注释、文案或样式片段。

### 3.3 检查代码引入链

检查 `package.json`、锁定依赖、脚本配置和打包入口，确认外部项目是否以以下任一方式进入 ECHO：

- npm 运行时依赖。
- Git 子模块或 vendored 源码。
- 构建脚本下载或复制外部源码。
- 打包清单中的外部文件。
- 生产文件中的作者标识、许可证头或仓库 URL。
- 通过测试夹具、生成文件或构建产物间接打包。

复核结果是：`package.json` 中只有 Playwright、Vitest、jsdom、fake-indexeddb、fflate 等开发和测试工具；没有上述六个功能项目，也没有对应运行时库。生产文件中未发现外部仓库名、作者名或许可证头被导入。

### 3.4 专属表达反查

针对外部项目提取具有识别性的表达进行全仓库搜索，包括：

- 外部函数名和调用链名称。
- 外部存储键和命名空间。
- 外部面板 ID、按钮 ID 和 CSS 类名。
- 外部状态标识和特殊字符串。
- 外部用户脚本专属前缀。
- 外部项目独有的整段 API 组织方式。

反查结果显示，这些表达没有出现在 ECHO 生产实现中；相关命中主要位于历史调研文档，用于描述外部项目本身。

### 3.5 Git 历史和工作区验证

检查功能引入相关 Git 历史、当前工作区状态和验证结果，确认审计不是建立在未保存或未检查的文件假设上。现有记录显示：

## 四、生产代码与外部项目的实现对照

### 4.1 B 站推荐历史

#### B 站外部项目的主要表达

`qiweiii/bili-feed-history` 的核心路径包括：

- `setupUI()`、`saveFeedItems()`、`addNavigationButtons()`。
- `navigateToPreviousFeed()`、`navigateToNextFeed()`、`replaceFeeds()`。
- 使用 `.feed-card` 作为卡片边界。
- 克隆整批卡片并将 HTML 保存到 `FeedHistoryItem.html`。
- 使用 `currentIndex` 管理批次位置。
- 使用 `bili-feed-history-nav`、`bili-feed-prev`、`bili-feed-next` 等专属 ID。
- 通过固定延时等待“换一换”完成。

`746505972/bilibili-feed-history` 的核心路径包括：

- 对 `MutationObserver` 的 `removedNodes` 进行监听。
- 使用 `checkAndSaveFeedCards()`、`saveFeedCard()` 和 `generateCardId()`。
- 克隆单卡并保存 `outerHTML`。
- 使用 `chrome.storage.local` 保存历史。
- 通过 `bilibili-feed-history-panel`、`history-content`、`history-card` 等专属标识构建独立面板。
- 使用 `cleanClonedElement()` 清理内联事件、`script` 和 `iframe[srcdoc]`。

#### B 站 ECHO 的实际表达

ECHO B 站模块采用了不同的数据和渲染模型：

- 使用 `captureBatch()`、`extractCard()`、`getFeedSlots()` 等 ECHO 自有函数组织批次采集。
- 保存结构化卡片数据，例如目标 URL、标题、封面、作者、时长、统计信息和展示类型，而不是保存整段站点 HTML。
- 使用 `chrome.storage.session` 通过 ECHO 后台消息服务保存当前标签页会话状态。
- 通过稳定的推荐卡片身份集合、数量和连续动画帧稳定性判断批次完成，而不是简单依赖固定延时。
- 使用 ECHO 专属 `echo-bili-*` 类名和 `ECHO Bili History` 日志前缀。
- 使用历史层覆盖展示结构化副本，不把副本节点插回 B 站 Vue 管理的原生列表。
- 对普通视频、番剧、直播和非 BV 目标保留目标 URL，不强制套用单一视频 ID 规则。

因此，虽然两类实现都解决“找回 B 站已被换掉的推荐”的产品问题，且都需要面对 `.feed-card` 等站点事实，但具体代码表达、数据模型、等待条件、存储位置、渲染方式和命名均不同。共同的产品目标和站点选择器不能单独构成代码复制证据。

### 4.2 知乎黑名单

#### 知乎外部项目的主要表达

外部知乎项目分别采用过以下方案：

- `pionxzh/userscripts`：`fetchData()`、`getBlockedUser()`、`blockByBlackList()`；使用 `GM_setValue('__zhihu_blocked_user__', result)`，按用户生成 CSS，使用 `:has()` 和 `sentinel.on()` 处理动态内容，并添加 `__BLOCKED__` 标记。
- `pionxzh/Zhihu-block`：使用 Cookie 保存精简名单，在整个文档上安装 MutationObserver，再按全量名单重扫。
- `jasonz3157/my-violentmonkey-scripts`：使用 `shurlormes-*` 命名空间、`b-{userId}` 存储键、固定 500 ms 轮询、隐藏内容备份恢复和可选 WebDAV 同步。
- `liuyubing233/zhihu-custom`：采用更大的脚本架构，包含本地名单与官方名单合并、多个页面处理器、接口响应处理和自己的 `Store`/处理函数体系。

这些项目都说明“官方黑名单同步”和“按作者 ID 过滤内容”是可以实现的产品路径，但每个项目的源码组织和产品边界不同。

#### 知乎 ECHO 的实际表达

ECHO 知乎模块采用了另一套工程组织：

- 使用 ECHO 自有的 `echoZhihuBlocklistV1` 数据根和 `EchoMessages` 消息协议。
- 使用账号分区快照，按当前知乎账号保存名单，避免把不同账号的屏蔽数据混在一起。
- 使用 Port 处理长时间同步，提供取消、断连处理、重试、超时和提交前一致性检查。
- 使用 `fetchPage()`、`syncBlocklist()`、`loadSnapshot()`、`startFilter()` 等 ECHO 自有函数组织同步与过滤生命周期。
- 从知乎页面结构化数据和作者链接中提取作者 ID，再用 `Set` 做过滤，不按每个黑名单用户生成一组 CSS 规则。
- 使用局部扫描、批量调度和 MutationObserver 处理动态节点。
- 使用 `echo-zhihu-*` 类名、数据属性和占位按钮，并保留用户临时展开被隐藏内容的路径。
- 不使用外部项目的 `__zhihu_blocked_user__`、`shurlormes-*`、`b-{userId}`、`__BLOCKED__` 等专属标识。

因此，ECHO 与外部项目共享的是知乎公开接口和页面字段这一事实层信息，以及“按稳定用户 ID 过滤”的一般工程思想；ECHO 没有复用外部项目的函数结构、存储方案、CSS 规则、脚本命名空间或动态处理表达。

## 五、审查发现

### 5.1 已排除或基本排除的风险

以下风险在当前可见仓库和审计基线中没有发现证据：

- 外部功能项目作为 ECHO 运行时依赖进入产品。
- 外部仓库源码以复制文件、子模块、构建产物或生成文件形式进入产品。
- 外部作者版权头或许可证头被删除后进入生产文件。
- 外部项目专属函数名、变量名、命名空间或 DOM ID 被直接保留。
- 外部项目成套 CSS、HTML 面板、文案或图标被直接搬入。
- ECHO 的 B 站模块保存外部项目所保存的整段 `outerHTML` 或批次 HTML 数据模型。
- ECHO 的知乎模块采用外部项目的 CSS 黑名单、固定轮询、Cookie 名单或 WebDAV 同步方案。
- Git 历史中出现明显的外部项目文件导入或直接复制路径。

### 5.2 保留为低概率、不可绝对排除的风险

以下事项不能通过最终仓库静态检查完全证明为零：

- 实现 agent 在某个未留存上下文中是否看过外部源码。
- 未进入当前仓库的中间代码草稿是否曾短暂存在。
- 外部项目在审计固定提交之后是否发生过许可证或代码变化。
- 仅凭人工结构对照无法给出一个数学意义上的“复制概率百分比”。
- 本次未运行专门的 token/AST 相似度工具，因此不能声称已经获得机器生成的相似度分数。

这些是审计能力边界，不是当前发现了相反证据。就最终交付物可检查的来源痕迹而言，现有证据支持风险极低的判断。
