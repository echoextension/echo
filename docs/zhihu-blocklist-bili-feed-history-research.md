# 知乎黑名单增强与 B 站推荐回退：产品调研与开源合规

> 调研日期：2026-08-25  
> 工作分支：`feature/zhihu-blocklist-bili-feed-history`  
> 状态：方向确认，尚未进入实现  
> 说明：本文记录产品判断与开源合规边界，不构成法律意见。

## 一、共同的产品命题

本轮候选功能都不是增加新的内容消费入口，而是修复中国主流网站中违背用户直觉的既有交互：

- 知乎的「屏蔽用户」没有可靠地阻止该用户的内容继续出现在推荐流、回答和评论中。
- B 站首页「换一换」是不可逆操作，误触后无法找回刚刚看到但尚未来得及打开的视频。

二者可以归纳为同一条产品方向：**把网站原本不完整或不可逆的用户控制，补成符合直觉、可预期的控制。** 这延续了 ECHO 从通用浏览器增强走向中国网站具体场景深度优化的演进。

## 二、知乎：让黑名单真正作用于内容

### 2.1 问题与预期

用户对「拉黑」的合理预期是：拉黑某个用户后，不再主动看到该用户本人发布的内容。知乎官方黑名单更偏向限制互动关系，不能稳定满足这一内容层预期。

ECHO 的目标应表述为：

> 用户在知乎拉黑某人后，ECHO 将其视为内容黑名单成员，并在支持的页面中隐藏该用户本人发布的内容。

首版建议覆盖：

1. 首页推荐流与关注流中的问题、回答、文章和想法。
2. 问题页中的回答。
3. 评论和子评论。
4. 同步知乎官方黑名单。
5. 用户在页面内新增或解除拉黑后，当前会话及时更新。

首版暂不扩大到「别人引用、回复或讨论黑名单用户」的内容。过滤对象应以内容作者为准，避免因为正文提及某个用户而误伤正常内容。

### 2.2 已有项目验证

参考项目：[liuyubing233/zhihu-custom](https://github.com/liuyubing233/zhihu-custom)（知乎修改器）。调研时用户脚本版本为 `5.21.4`，仓库仍在维护。

该项目已经验证以下能力可行：

- 从知乎接口分页同步官方黑名单。
- 以稳定的用户 ID，而不是昵称，识别黑名单成员。
- 在推荐列表、问题回答、用户主页和评论区过滤黑名单用户内容。
- 在知乎黑名单之外维护本地黑名单，并合并两类名单进行匹配。
- 监听知乎的动态页面与评论加载，在新增内容出现后继续过滤。

这说明需求真实且可以实现，但也提示两个产品风险：知乎页面和数据结构变化频繁；黑名单同步、作者识别和动态内容过滤必须被视为长期维护能力，而不是一次性选择器适配。

### 2.3 推荐的 ECHO 范围

ECHO 不应复制「知乎修改器」的大而全形态。建议保持单一承诺：**拉黑之后，不再看到此人本人发布的内容。**

建议首版产品行为：

- 功能默认开启或在首次进入知乎时给出一次明确说明，最终默认策略在实现前确认。
- 过滤后直接收起内容，不在信息流中留下大面积占位。
- 提供轻量的临时查看入口，降低误判时的不可恢复感。
- 设置页只提供总开关、官方黑名单同步状态和必要的故障说明。
- 本地补充名单属于后续候选；首版可先围绕官方黑名单闭环，避免同时引入名单管理产品。

### 2.4 需要进一步实测的问题

- 未登录、登录和知乎不同页面版本下，官方黑名单接口是否一致可用。
- 推荐流中问题作者与回答作者同时存在时，应以当前卡片实际展示内容的作者为准。
- 评论回复对象命中黑名单时，不应误删非黑名单作者的评论。
- 知乎在页面内拉黑后，能否稳定捕获状态变化并立即过滤。
- 官方黑名单是否存在数量上限，以及 ECHO 是否有必要在首版提供本地名单兜底。

## 三、B 站：让「换一换」可以回退

### 3.1 问题与预期

用户点击 B 站首页「换一换」后，上一批推荐立即消失。误触或操作过快时，用户无法找回刚扫到的感兴趣视频。

核心需求不是建立一个新的观看历史中心，而是：

> 点击「换一换」之后，可以立即回到上一批推荐，并能在已经浏览过的批次间前进和后退。

### 3.2 已有项目验证

#### 方案 A：按批次前进和后退

参考项目：[qiweiii/bili-feed-history](https://github.com/qiweiii/bili-feed-history)。

该项目在「换一换」附近增加前进、后退按钮，以批次保存当前推荐卡片，最多保留最近 10 批，并把选中的历史批次重新显示在首页推荐区域。该形态与本需求最贴合。

#### 方案 B：长期推荐历史面板

参考项目：[746505972/bilibili-feed-history](https://github.com/746505972/bilibili-feed-history)。

该项目监听页面中被替换的推荐卡片，将视频卡片按单条记录保存在本地，并通过侧边面板展示历史。它更像「曾经出现过的推荐视频收藏箱」，适合长期检索，但比误触撤回更重。

### 3.3 推荐的 ECHO 范围

首版建议采用方案 A 的产品形态，但进行 ECHO 自己的交互设计与独立实现：

- 在原生「换一换」附近提供「上一批」和「下一批」。
- 初始状态和历史边界下，按钮应明确禁用。
- 每次原生刷新成功后记录一个批次，而不是把所有视频拆成无边界历史库。
- 建议仅保留当前标签页最近 10 批；是否跨刷新持久化可在实测后决定。
- 回看历史批次时，不应被误记录成新的推荐批次。
- 用户从历史批次点击视频时，应保持原视频链接可正常打开。

完整历史面板可作为后续候选，不应成为首版主体。首版优先解决「刚刚那一屏找回来」这一高频、低理解成本的任务。

### 3.4 产品边界

所谓「回退」是恢复已经在客户端展示过的推荐卡片，不是让 B 站服务端推荐算法回滚。因此：

- 返回旧批次不会撤销 B 站已经发生的推荐请求。
- 旧卡片中的实时数据可能已经过期。
- 页面刷新、关闭标签页或 B 站改版后，历史是否保留取决于最终存储策略。
- 应避免把整段未经处理的页面 HTML 长期保存，以降低兼容性、安全性和存储成本风险。

### 4.2 「公开仓库」不等于「开源许可证授权」

GitHub 仓库公开，只代表他人可以查看，并可通过 GitHub 提供的功能进行 fork。GitHub 服务条款授予的站内查看和 fork 权利，不能替代软件许可证，也不自动授予在 ECHO 中复制、修改、发布代码的权利。

没有许可证时，默认版权仍归作者所有。可以研究公开行为、讨论需求、学习一般思想和独立解决同一问题，但不应复制受版权保护的具体表达，包括源码、成套样式、文案、图标和截图。

### 4.3 MIT 与 ECHO GPL-3.0 的关系

ECHO 当前采用 GPL-3.0。MIT 许可代码通常可以并入 GPL-3.0 项目，但需要同时满足：

1. 保留 MIT 代码原有的版权声明和 MIT 许可文本。
2. 明确记录引用文件、上游仓库、作者、版本或提交，以及 ECHO 所做修改。
3. 组合后的 ECHO 发布物继续按 GPL-3.0 提供完整对应源代码。
4. 不把上游 MIT 代码错误标记为 ECHO 原创，也不删除上游归属。

由于 `zhihu-custom` 仓库没有标准 `LICENSE` 文件，虽然脚本头和 `package.json` 对 MIT 的声明已经构成明确许可证据，ECHO 仍采用更保守的做法：**不直接移植其实现；如后续确有必要复用实质性代码，先联系作者确认版权声明写法。**

## 五、实施阶段的洁净实现规则

本分支后续开发应遵守以下规则：

1. 外部项目只用于确认需求、交互形态和可行性，不把其源码复制到工作区作为起点。
2. 根据知乎/B站实际页面行为、公开网络请求和 ECHO 自身架构重新设计实现。
3. 不复用两个无许可证 B 站项目的函数结构、变量命名、成套 CSS、文案、图标或页面布局。
4. 对 `zhihu-custom` 同样优先独立实现；若出现必要引用，先在本文增加来源、提交、文件、引用范围和许可证履行清单，再写代码。
5. 在 PR 或发布说明中保留本调研文档，确保产品来源与代码来源可以区分。
6. 发布前再次检查所有新增文件，不得残留未经授权的第三方代码或资产。

## 六、建议的交付顺序

两个功能共享产品主题，但站点依赖和验证方式不同，建议在同一分支中分阶段交付：

1. 先完成 B 站推荐批次回退。需求边界清晰，可快速验证交互价值。
2. 再完成知乎官方黑名单同步和首页/回答过滤。
3. 最后补评论区动态过滤，并针对不同页面版本做回归验证。
4. 两个模块均应提供独立开关，任何一个站点适配失败都不影响 ECHO 的通用功能。

## 七、进入实现前的决策项

- 知乎增强是否默认开启，还是默认关闭并由用户主动启用。
- 知乎首版是否包含本地补充黑名单。
- 被过滤内容是否提供「临时查看」入口。
- B 站历史仅保留当前标签页，还是跨刷新保存最近批次。
- B 站首版保留 5 批还是 10 批。
