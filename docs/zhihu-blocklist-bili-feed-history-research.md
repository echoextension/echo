## 结论摘要

- **知乎黑名单增强：高难度，但已有充分的实现先例，结论为 Prototype-Go。** `zhihu-custom` 当前源码已经把官方 `blocked_users.id` 直接用于匹配推荐流和问题回答的 `author_member_hash_id`，并递归处理评论接口中的子评论；`pionxzh` 与 `jasonz3157` 又分别验证了 CSS/Sentinel 和纯 DOM 轮询路径。ECHO 不需要从零猜测，只需要复现最稳健的数据链并针对评论标识做补强。
- **B 站推荐历史：中等偏高难度，结论为 Go。** `qiweiii/bili-feed-history` 已实现原位前后翻 10 个批次；`746505972/bilibili-feed-history` 已实现从被移除 DOM 收集单卡并在独立面板恢复链接。ECHO 可以选取二者已验证的产品优点，使用结构化数据独立实现。
- 知乎真正困难的部分不是过滤本身，而是 2,000 人以上名单同步耗时、评论作者的 `id`/`url_token` 对齐、多账号缓存和网站改版维护。它们应转化为明确工程任务，而不是据此否定功能。
- B站真正困难的部分是批次完成判定和非普通视频卡片建模，不是找不到捕获入口。2026-08-26 实测确认当前“换一换”稳定替换 10 个 `.feed-card`，与参考项目的批次模型一致。
- 两个功能均采用独立模块、独立开关和失效放行。站点结构不识别时停止处理，不影响 ECHO 通用功能。
- 2026-08-27 首轮实现与人工冒烟暂时通过；这不是发布结论。后续以较长时间狗粮测试验证稳定性，并另行研究欢迎页与官网的功能呈现。

## 一、共同的产品命题

本轮候选功能都不是增加新的内容消费入口，而是修复中国主流网站中违背用户直觉的既有交互：

- 知乎的「屏蔽用户」没有可靠地阻止该用户的内容继续出现在推荐流、回答和评论中。
- B 站首页「换一换」是不可逆操作，误触后无法找回刚刚看到但尚未来得及打开的视频。

二者可以归纳为同一条产品方向：**把网站原本不完整或不可逆的用户控制，补成符合直觉、可预期的控制。** 这延续了 ECHO 从通用浏览器增强走向中国网站具体场景深度优化的演进。

## 二、知乎：让黑名单真正作用于内容

### 2.1 问题与预期

用户对「拉黑」的合理预期是：拉黑某个用户后，不再主动看到该用户本人发布的内容。知乎官方黑名单更偏向限制互动关系，不能稳定满足这一内容层预期。

ECHO 的开发目标应表述为：

> 用户在知乎拉黑某人后，ECHO 在已验证支持且能可靠识别作者的页面中，尝试隐藏该用户本人发布的内容。

首版开发与验收范围：

1. 首页推荐流与关注流中的问题、回答、文章和想法。
2. 问题页中的回答。
3. 评论和子评论。
4. 同步知乎官方黑名单。
5. 用户在页面内新增或解除拉黑后，当前会话及时更新。

首版暂不扩大到「别人引用、回复或讨论黑名单用户」的内容。过滤对象应以内容作者为准，避免因为正文提及某个用户而误伤正常内容。

### 2.2 已有项目验证

> **阅读边界：** 本节是对公开项目现状的技术调研，用于展示已经有人尝试过哪些路径、各自付出了什么成本。项目行为、下文的比较以及“可借鉴点”都不代表 ECHO 已确认的产品范围、架构决策、实现顺序或验收契约；是否采用其中任何做法，仍需单独评审。

#### 项目 A：`liuyubing233/zhihu-custom`

参考项目：[liuyubing233/zhihu-custom](https://github.com/liuyubing233/zhihu-custom)（知乎修改器）。调研时用户脚本版本为 `5.21.4`，仓库仍在维护。

该项目已经验证以下能力可行：

- 从知乎接口分页同步官方黑名单。
- 以稳定的用户 ID，而不是昵称，识别黑名单成员。
- 在推荐列表、问题回答、用户主页和评论区过滤黑名单用户内容。
- 在知乎黑名单之外维护本地黑名单，并合并两类名单进行匹配。
- 监听知乎的动态页面与评论加载，在新增内容出现后继续过滤。

参考实现的同步接口为：

```text
GET https://www.zhihu.com/api/v3/settings/blocked_users?offset={offset}&limit={limit}
```

请求在 `www.zhihu.com` 登录页面内发起，通过 `credentials: "include"` 使用浏览器已有登录态；插件无需读取、复制或保存 Cookie。响应提供 `data[].id`、`data[].url_token` 和 `paging`：分页能力已经实测，两个身份字段能否分别覆盖各页面作者仍需交叉验证。新增或解除拉黑则可使用 `/api/v4/members/{url_token}/actions/block`，写操作需要 XSRF 处理，但当前研究范围不主动代理原生拉黑操作。

该项目的官方黑名单同步是**用户在脚本设置面板点击“同步知乎黑名单”后手动触发**，不是定时任务。实现以 `limit=20` 从 `offset=0` 递归分页；加载中显示“已读取人数 / `paging.totals`”，完成后以本次完整结果替换官方名单缓存，并保留同一用户原有的本地标签。官方名单与脚本本地补充名单分开保存；同步结束时，会从本地补充名单中移除已进入官方名单的重复成员。

页面过滤主要使用以下数据链路：

- 推荐流和问题回答从 `data-za-extra-module.card.content.author_member_hash_id` 提取稳定作者 ID，再与名单构建的 `Map` 匹配。
- 评论作者信息来自知乎评论接口响应中的 `author.id`、`author.url_token`，页面链接作为辅助识别来源。
- 推荐流、回答、评论和用户主页使用不同处理器；已处理节点会添加标记，部分入口带 500 ms 级节流或重试。
- 可选择整项隐藏，或把正文替换为 `***` 并保留黑名单标签。
- 脚本拦截页面 `fetch`，用推荐、回答、评论等接口响应补足 DOM 中不易稳定取得的数据，并监听原生拉黑/解除接口以更新本地名单。

从源码可见的局限包括：同步函数没有完整展示 HTTP 状态、响应结构异常和递归中途失败后的 UI 恢复；缓存没有明显按当前知乎账号分区；作者识别和动态处理依赖知乎内部字段、接口及页面类名。它证明了“手动同步 + 本地名单 + 多页面过滤”是一条实际使用中的路径，但不自动证明其全部实现细节适合 ECHO。

#### 项目 B：`pionxzh/userscripts` 的知乎助手

参考项目：[pionxzh/userscripts](https://github.com/pionxzh/userscripts/tree/main/packages/zhihu)。该仓库使用标准 MIT 许可证；知乎助手最近一次仓库代码推送时间为 2023-11，活跃度低于 `zhihu-custom`。

该项目采用**脚本启动时自动同步**：`blockByBlackList()` 调用 `getBlockedUser()`，从官方 `blocked_users` 接口以 `limit=20` 递归读取全部分页。同源 `fetch` 没有显式填写 `credentials`，但默认会携带同源凭据。递归成功时通过 `GM_setValue('__zhihu_blocked_user__', result)` 缓存结果；请求或解析抛错时返回 `GM_getValue` 中的旧缓存。

它没有为每个新增卡片执行 JavaScript `Set` 查询，而是按黑名单成员生成成组 CSS：

- 回答和搜索结果使用 `:has()`、作者 `meta[itemprop="name"]` 等选择器隐藏整张卡片。
- 评论使用用户主页链接、头像 `alt` 和昵称组合定位，并可隐藏评论正文、划掉或替换作者名称。
- 搜索结果的部分动态处理交给 `sentinel-js`，由选择器命中新节点后添加屏蔽类。

这一实现的优势是过滤后主要交给浏览器样式系统，不需要持续遍历所有卡片；但名单达到数千人时会生成大量 CSS 选择器和字符串。部分规则依赖昵称或同时依赖昵称与链接，昵称变更、重名、特殊字符转义和知乎 DOM 改版都可能影响匹配。缓存写入发生在递归回溯过程中，而不是清晰的单次最终提交；因此它更适合作为“自动同步和 CSS 驱动过滤确实有人实践过”的证据，不足以单独证明大名单下的性能与一致性。

#### 项目 C：`pionxzh/Zhihu-block`（已废弃）

参考项目：[pionxzh/Zhihu-block](https://github.com/pionxzh/Zhihu-block)。仓库 README 已标记 `DEPRECATED`，后续迁移到上述 `pionxzh/userscripts`；README 声明 MIT。

这是较早的自动同步实现：每次脚本初始化后递归请求官方名单，保存 `{id, name, url_token}`；为跨 `www.zhihu.com` 与专栏子域共享数据，它没有继续使用 `localStorage`，而是把精简后的名单 JSON 写入有效期 7 天的站点 Cookie。接口失败（注释中特别提到专栏页面 401）时恢复 Cookie 缓存。

过滤器遍历名单，为每个用户执行多条 jQuery `:has()` 查询，覆盖关注流、话题、回答和评论。它在整个 `document` 上安装 `MutationObserver({childList:true, subtree:true})`；只要新增节点，就重新调用一次全量 `blockContent()`。

该方案提供了历史价值：它验证了官方名单、不同知乎子域和动态页面过滤早已是实际问题。但 Cookie 容量通常只有数 KB，无法承载数千人名单；“每次 DOM 变化 × 全名单 × 多选择器”的处理方式也不适合作为当前性能基线。它应被视为历史实现样本，而非现代推荐方案。

#### 项目 D：`jasonz3157/my-violentmonkey-scripts`

参考项目：[jasonz3157/my-violentmonkey-scripts](https://github.com/jasonz3157/my-violentmonkey-scripts/blob/master/zhihu-blocker-user.js)。调研时脚本版本为 `0.13`，仓库在 2026-08 仍有提交；用户脚本头声明 GPL-3.0。

该项目更接近“在知乎页面内维护一套可操作的本地屏蔽名单”：

- 首次运行时从官方 `blocked_users` 接口导入，随后写入 `shurlormes-synced`，以后启动不会重复做官方全量导入。
- 请求初始 URL 写 `limit=100`，后续直接跟随 `paging.next`；当前知乎实际仍会硬限制为每页 20 人。
- 官方导入把每个用户保存为 `localStorage` 中的 `b-{userId}` 项，同时在 `GM_setValue` 保存归一化 ID 数组。
- 同步过程只添加官方返回的用户，没有在全量结束后删除“本地存在但官方已不存在”的 ID，因此语义是初次导入或集合补充，不是官方名单的严格镜像。
- 回答作者优先读取 `data-za-extra-module.card.content.author_member_hash_id`，失败时回退到作者主页链接；评论作者从 `/people/{token}` 链接提取。
- 回答和评论旁会插入屏蔽/取消按钮；点击后立即修改本地名单，并调用知乎成员接口查询 `url_token`，再调用官方拉黑或解除接口。
- 支持“替换为 `[已屏蔽]`”和“删除整个用户内容容器”两种强度，也支持名单导入、导出及可选 WebDAV 跨设备同步。
- 页面动态处理采用每 500 ms 调用一次 `mainEvent()` 的轮询：标记回答与评论、追加按钮、过滤内容并修复折叠回答。

这一项目验证了本地名单、页面内即时操作和跨设备同步可以独立于“每次全量镜像官方名单”存在。与此同时，500 ms 全页轮询、按用户拆分大量 `localStorage` 键、用 `innerHTML` 保存和恢复原内容，以及导入时可能批量调用知乎写接口，都带来不同的性能、稳定性和风险取舍。WebDAV 同步还会把屏蔽 ID 发送到用户配置的第三方服务器，与 ECHO 当前的纯本地隐私边界不同。

#### 四类实现横向对照

| 项目 | 官方名单触发方式 | 本地数据语义 | 作者识别 | 动态内容处理 | 维护状态 |
| --- | --- | --- | --- | --- | --- |
| `zhihu-custom` | 设置面板手动全量同步 | 官方名单镜像 + 独立本地补充名单 | 结构化稳定 ID 为主，评论接口补足 | 接口拦截、分页面处理、节流/重试 | 2026 年仍维护 |
| `pionxzh/userscripts` | 每次脚本启动自动全量同步 | 官方名单缓存，失败回退旧值 | 链接、昵称、meta 等组合 | 大量生成 CSS + `sentinel-js` | 2023 年后少有更新 |
| `pionxzh/Zhihu-block` | 每次启动自动全量同步 | 7 天 Cookie 缓存 | 用户 ID、URL Token、部分昵称 | 全文档 MutationObserver 后全量重扫 | 已废弃 |
| `jasonz3157` | 首次启动导入，之后本地维护 | 本地 ID 集合，可选 WebDAV 合并 | 结构化 ID + 作者链接回退 | 每 500 ms 页面轮询 | 2026 年仍有提交 |

#### 可供后续评审的启示（非决策）

以下只是基于外部实现的分析建议，**不构成最终开发契约**：

- 手动同步不是未经实践的退让方案；维护较活跃、功能覆盖最完整的 `zhihu-custom` 正在采用手动同步并显示分页进度。
- “启动时自动同步”也有公开先例，但现有样本没有同时解决大名单性能、多账号隔离、精确删除同步和完整失败恢复，不能仅凭其存在就判断自动方案更成熟。
- 稳定作者 ID 比昵称更可靠；多个项目都逐步转向 `author_member_hash_id` 或用户链接，昵称匹配更适合作为兼容回退而非唯一依据。
- 动态过滤已有四种实践：接口拦截、Sentinel/选择器监听、MutationObserver、固定间隔轮询。它们分别在数据完整性、页面侵入、维护成本和运行开销上有不同取舍，需要结合 ECHO 范围另行评审。
- 数千人场景下，按用户生成 CSS、每次 DOM 变化遍历全名单、500 ms 全页轮询都值得专门压测；调研信息本身不能替代 ECHO 的实际性能验证。
- 本地补充名单、导入导出、页面内即时拉黑、WebDAV 同步均已有项目实践，但它们是彼此独立的产品能力，不应因为参考项目同时提供就自动进入 ECHO 范围。

### 2.3 推荐的 ECHO 范围

ECHO 不应复制「知乎修改器」的大而全形态，但可以围绕一个清晰承诺开发：

> 用户同步知乎黑名单后，ECHO 在推荐流、关注流、问题回答和评论区隐藏黑名单用户本人发布的内容。

这不是对未来所有知乎页面结构的永久保证，但首版列出的四类入口应作为明确验收范围，而不是只做模糊的“尽力隐藏”。无法识别作者时放过内容并计入诊断，不使用昵称猜测。

候选首版产品行为（尚待确认）：

- 实验期默认关闭，由用户主动开启；稳定性达到验收标准后再讨论默认策略。
- 过滤后直接收起内容，不在信息流中留下大面积占位。
- 提供轻量的临时查看入口，降低误判时的不可恢复感。
- 设置页提供总开关、手动同步按钮、成员数量、最近成功时间、同步进度和错误状态；是否显示账号匿名标识取决于是否支持多账号隔离。
- 本地补充名单属于后续候选；首版可先围绕官方黑名单闭环，避免同时引入名单管理产品。

首版按两阶段实现：

1. **阶段 A：列表与回答。** 同步官方名单，以 `blocked_users.id` 建 `blockedIds`；从 `data-za-extra-module.card.content.author_member_hash_id` 读取当前内容作者并隐藏整张卡片。这条链路已经被 `zhihu-custom` 和 `jasonz3157` 分别实现。
2. **阶段 B：评论与子评论。** 从评论作者链接 `/people/{pathValue}` 提取路径值，并以 `blockedIds` 匹配。2026-08-26 的真实黑名单评论样本证明当前路径值直接命中 `blocked_users.id`，而不是 `blocked_users.url_token`。只检查评论作者，不因回复对象命中而隐藏评论；递归扫描子评论容器。

阶段 A 可以先独立发布，阶段 B 在评论样本验证通过后追加。这样评论适配不会阻塞推荐流和回答这一主体价值。

### 2.5 登录态与名单获取机制

无论采用手动还是自动触发，底层获取链路相同：

1. 知乎内容脚本通过 `/api/v4/me` 或页面 `js-initialData` 确认当前账号稳定 ID。
2. 在知乎页面的同源上下文中只读调用官方黑名单接口，浏览器自动附带当前登录态。
3. 按服务端允许的分页大小顺序拉取，响应暂存在本次任务的内存或临时存储中。
4. 每页校验结构、总数、稳定 ID 和重复项；全部完成后才生成新快照。
5. 全部完成后保存新名单；若中途失败，不应用明显不完整的结果。

#### 推荐方案：设置页手动同步

用户在 ECHO 设置页主动点击“同步知乎黑名单”，扩展通过已打开且已登录的知乎标签页执行分页请求，并显示“已读取人数 / 官方总数”和预计等待时间。2,097 人实测约需 2 分 32 秒；即使更大名单需要数分钟，只要进度明确、可以取消且不会阻塞正常浏览，这一成本并非不可接受。

该方案只是风险相对较低，不是简单功能。同步任务跨越设置页、知乎内容脚本和本地存储；若用户关闭标签页、切换账号、扩展更新或 MV3 上下文被回收，必须能明确失败并保留旧快照。任务需要长连接或可恢复协议，单次 `sendMessage` 不适合承载数分钟进度会话。

最低要求包括：同步期间禁止并发任务、显示账号和进度、允许取消、有限重试、冷却时间、任务超时、完整成功后原子替换、失败保留旧快照，并在应用快照前再次校验当前账号。若没有打开且已登录的知乎标签页，只能提示用户打开知乎后重试。

它的局限同样明确：用户在知乎新增或解除拉黑后，ECHO 的本地名单不会自动变化；换设备或切换知乎账号后，也需要用户重新同步。这些可以通过界面提示说明，不必自动等同为首版阻断项。

#### 排除项：启动时或定时自动全量同步

按当前 2,097 人样本，自动全量同步会无感发起 105 次请求并持续约 2.5 分钟；5,000 人约 250 次、6 分钟。一次实测未触发限流，不足以证明这种行为对用户账号和知乎服务长期安全。

因此启动时同步、每次打开知乎同步、固定周期后台全量同步均不进入当前方案。未来若能找到官方增量游标、可靠的拉黑事件增量记录，或由用户明确授权的低频校准，再单独立项评估，不能作为本功能的自然延伸。

### 2.6 大名单实测方法

为避免在正式代码中凭假设设计，仓库提供独立的本地 MV3 调研扩展：

- 工具目录：`crawler/zhihu-blocklist-probe/`
- 匿名基线报告：`crawler/echo-zhihu-blocklist-probe-2026-08-25T15-14-21-424Z.json`
- 运行范围仅为 `https://www.zhihu.com/*`，只发起 GET 请求。
- 快速模式测试 `limit=20/50/100`；完整模式串行读取全部分页，请求间隔 250 ms。
- 对 `429` 和服务端错误进行有限指数退避，支持用户停止。
- 报告不含姓名、原始用户 ID、URL Token、Cookie 或响应正文；仅保留聚合指标和账号 ID 的 SHA-256 截断值。

该工具被版本控制以支持跨设备、跨账号和跨知乎版本复测，但不在 ECHO 正式 `manifest.json` 中注册，不进入生产扩展运行链路。

### 2.7 2026-08-25 实测结果

测试环境为 Windows 10/11 兼容 UA、Chrome/Edge Chromium 151 登录态，完整扫描结果如下：

| 指标 | 实测结果 |
| --- | ---: |
| `/api/v4/me` 登录态确认 | HTTP 200，72 ms |
| 官方报告总人数 | 2,097 |
| 实际唯一 `id` | 2,097 |
| 实际唯一 `url_token` | 2,097 |
| 请求 `limit=20/50/100` 的实际返回数 | 均为 20 |
| 完整分页数 | 105 |
| 正常满页 / 末页 | 104 × 20 / 1 × 17 |
| 接口累计耗时 | 126,166 ms |
| 加 250 ms 页间隔的墙钟估算 | 152,166 ms（约 2 分 32 秒） |
| 总响应体积 | 1,145,645 字节（约 1.09 MiB） |
| 单页平均 / P95 / 最大耗时 | 1,201.6 / 1,294 / 1,778 ms |
| 重复 ID / 缺失 ID | 0 / 0 |
| 重试或限流 | 0 |
| 所有分页的 `paging.totals` | 始终为 2,097 |

结论：接口可以取回官方后台 UI 无法完整展示的全部名单，数据在本次静态扫描中完整一致；但每页 20 人是服务端硬限制，客户端不能通过提高 `limit` 降低请求数。按相同速度估算，5,000 人约需 250 个请求和 6 分钟。末页虽然 `paging.is_end=true`，仍存在 `paging.next`，因此正式实现必须以 `is_end` 为主要终止依据，并用计数和最大页数作为防御性约束。

一次成功扫描不能证明长期不会限流，也不能覆盖扫描期间名单发生增删的情况。该结果支持“可实现”；同时更支持由用户显式、低频触发，而不是每次打开知乎都全量同步。

### 2.8 同步状态与一致性要求

手动同步仍然需要完整状态设计，以下不是增强项，而是进入产品的最低条件：

- 同一次手动同步只运行一个任务，重复点击不重复发起请求。
- 只有到达 `is_end=true` 且唯一人数与 `totals` 一致时才保存新名单。
- 任一分页失败时保留上次成功名单，并向用户显示失败位置。
- 设置最大页数、总任务时限和有限重试，防止异常分页无限运行。
- 快照必须按知乎稳定账号 ID 分区；每次过滤前确认当前账号与快照账号一致。
- 切换账号、退出登录或无法确认账号时立即停用过滤，不允许沿用最近一个账号的名单。
- 同步开始和结束都记录账号 ID；中途账号变化时丢弃本次结果。
- 扫描完成后复查总数或首尾锚点。由于 `offset` 分页没有快照隔离，即使数量一致仍不能数学上证明无漏项，UI 不应显示“绝对完整”。
- 数分钟任务必须有明确所有者。设置页关闭、知乎标签关闭、扩展上下文回收时要进入可解释的取消或失败状态。

黑名单属于账号关系数据，只应存入 `chrome.storage.local`，不应放入 `chrome.storage.sync`。`sync` 区总量和单项配额较小，还会跨设备上传；这里只适合保存功能开关和同步周期。正式发布前必须同步更新隐私政策，明确 ECHO 会在本地处理知乎账号标识、黑名单关系和页面作者标识，但不会上传这些数据。

### 2.9 ECHO 过滤方案与公开实现依据

加载成功快照后，在每个知乎顶层页面构建稳定 ID 内存集合：

```text
blockedIds: Set<stable-user-id>
```

`blocked_users.id` 同时用于列表、回答和当前评论作者主页路径。`url_token` 仍随快照保存，供成员资料或接口兼容诊断使用，但不作为当前 DOM 评论的主匹配键：

- `zhihu-custom` 同步时保存 `{ id, name, urlToken: url_token }`；列表和回答建立 `Map<id, user>`，直接查询 `card.content.author_member_hash_id`。
- `jasonz3157` 的回答处理同样优先读取 `author_member_hash_id`，取不到时回退到作者主页链接。
- `pionxzh/Zhihu-block` 对评论同时尝试 `/people/{id}` 与 `/people/{url_token}`，说明两类标识必须分别验证，不能预设路径命名空间。

2026-08-26 组合探针对同一真实样本并行验证了五条路径：主页路径直接匹配 `id` 成功、直接匹配 `url_token` 失败；成员资料解析后的 `id` 与 `url_token` 均成功；评论接口 `author.id` 与 `author.url_token` 均成功；姓名也命中但不作为可靠依据。因此首版评论明确使用 `blockedIds.has(pathValue)`，成员资料和评论接口仅作为未来结构变化时的兼容回退候选。

因此 ECHO 首版不需要 MAIN world，也不需要覆盖页面 `fetch`。默认 MV3 `ISOLATED` 内容脚本已经能够读取 `data-za-extra-module`、作者链接和新增 DOM。`zhihu-custom` 拦截评论接口主要用于给页面增加拉黑按钮所需的完整作者对象；如果 ECHO 首版只做过滤，DOM 中的 URL Token 足以完成匹配。只有实测发现某类评论没有作者链接时，才评估主动请求或最小 MAIN world 桥接。

名单规模不是主要性能瓶颈。构建索引为 $O(N)$，卡片匹配近似 $O(1)$；2,097 人甚至更大名单对 `Set.has()` 的成本很低。实际风险来自 DOM 查询、JSON 属性解析、全页重复扫描和多个观察器。

实现约束：

- 禁止按数千用户生成 CSS 选择器；禁止 500 ms 全页轮询；禁止在整个 `document.body` 每次变更后全量重扫。
- 只观察信息流、回答列表和已打开评论容器，不观察整个 `document.body` 后反复全页扫描。
- 只处理 MutationObserver 的 `addedNodes`，使用 `requestAnimationFrame` 合并同一帧变更。
- 用 `WeakSet` 或私有属性标记已处理节点；设置变化时才显式重新评估。
- 每个页面初始化时读取一次快照，禁止每张卡片调用 `chrome.storage`。
- 选择器、JSON 或作者标识解析失败时放过内容并记录本地诊断计数，避免误伤。
- 首版采用 CSS 类隐藏和轻量“临时查看”，不要用 `innerHTML` 重写知乎内容。

建议性能验收基线：初始 100 张卡片过滤不产生超过 50 ms 的单个长任务；每批 20 个新增节点处理目标低于 16 ms，最迟下一帧完成；关闭功能后不保留站点观察器；正常浏览期间不产生轮询网络请求。

还必须增加正确性指标：每种页面至少准备已拉黑、未拉黑、匿名、机构号、已注销、回复黑名单用户但作者未拉黑等样本；漏过滤率和误过滤率分别记录。任何误删未拉黑作者内容都是阻断缺陷，不能以“总体准确率高”接受。

### 2.10 ECHO 模块拆分与可复现实验

建议新增独立 `zhihu-tool/` 模块，不把站点逻辑并入全局 `content.js`：

| 模块 | 职责 |
| --- | --- |
| `zhihu-tool/sync.js` | 在知乎标签页读取账号与官方名单，分页进度、取消、失败保留旧快照 |
| `zhihu-tool/identity.js` | 归一化 `id`、`url_token`、作者链接和卡片属性；构建双索引 |
| `zhihu-tool/filter.js` | 处理列表、回答、一级评论和子评论；只添加/移除 ECHO 私有隐藏类 |
| `zhihu-tool/lifecycle.js` | 绑定局部观察器、SPA 重置、设置变化和销毁 |

原型实验按以下顺序执行，每一步都会产出聚合报告，不保存用户名或原始内容：

1. **身份链实验：** 从已同步名单选取当前页面实际出现的命中项，记录 `blockedIds.has(author_member_hash_id)` 与 `blockedIds.has(commentPathValue)` 的命中数量；人工抽查命中内容确属已拉黑用户。
2. **列表/回答实验：** 在推荐、关注和问题页分别滚动加载至少 100 项，记录总节点、可解析作者、命中、未知作者和处理耗时。解析失败只记录计数，不隐藏。
3. **评论实验：** 展开一级评论和至少两层子评论，比较评论作者 Token 与回复对象 Token，验证只按索引 0 的实际作者决定隐藏。这直接复现 `zhihu-custom` 的处理语义。
4. **动态加载实验：** 分别验证滚动加载、点击“更多评论”、打开/关闭评论弹窗和 SPA 跳转；确保新增节点只处理一次。
5. **账号切换实验：** 使用两个测试账号切换，缓存以账号 ID 分区；当前账号没有对应快照时暂停过滤并提示同步。
6. **性能实验：** 2,097 人名单下连续浏览 30 分钟，记录单批处理耗时、Long Task、观察器回调次数和已处理节点数量。

通过标准：支持范围内作者解析率达到 100%；已知黑名单样本全部隐藏；未拉黑、匿名和仅回复黑名单用户的评论零误删。若某一页面结构无法达到标准，只缩小该页面支持范围，不否定其他已通过阶段。

### 2.11 尚待实测的问题

- 未登录、Cookie 过期、验证码、风控和不同知乎页面版本下的失败响应。
- 扫描期间新增或解除拉黑时，`offset` 分页是否出现重复或漏项。
- 连续多次完整扫描、更多设备和 5,000 人以上账号是否触发限流。
- 同一浏览器切换知乎账号时，账号检测与缓存隔离是否及时可靠。
- 推荐流中问题作者与回答作者同时存在时，应以当前卡片实际展示内容的作者为准。
- 评论回复对象命中黑名单时，不应误删非黑名单作者的评论。
- 知乎在页面内拉黑后，能否稳定捕获状态变化并立即过滤。
- 官方黑名单实际数量上限，以及 ECHO 是否有必要提供本地名单兜底。

## 三、B 站：让「换一换」可以回退

### 3.1 问题与预期

用户点击 B 站首页「换一换」后，上一批推荐立即消失。误触或操作过快时，用户无法找回刚扫到的感兴趣视频。

核心需求不是建立一个新的观看历史中心，而是：

> 点击「换一换」之后，可以立即回到上一批推荐，并能在已经浏览过的批次间前进和后退。

### 3.2 已有项目验证

#### 方案 A：按批次前进和后退

参考项目：[qiweiii/bili-feed-history](https://github.com/qiweiii/bili-feed-history)。

该项目在「换一换」附近增加前进、后退按钮，以批次保存当前推荐卡片，最多保留最近 10 批，并把选中的历史批次重新显示在首页推荐区域。该形态与本需求最贴合。

源码调用链已经完整闭环：

1. `setupUI()` 在启动时调用 `saveFeedItems()` 保存初始批次。
2. `addNavigationButtons()` 找到原生“换一换”，添加前后箭头，并在原生按钮点击 600 ms 后再次调用 `saveFeedItems()`。
3. `saveFeedItems()` 克隆当前全部 `.feed-card`，把批次 HTML、时间戳和 `currentIndex` 写入本地存储，最多保留 10 批。
4. `navigateToPreviousFeed()` / `navigateToNextFeed()` 改变索引，`replaceFeeds()` 将历史 `.feed-card` 一对一替换当前卡片。

这证明“最近批次栈 + 原位前后翻”已经有人实现并发布。其薄弱点不是方案不可行，而是固定 600 ms 可能遇到慢网，HTML 克隆也绑定 B站当前 DOM。ECHO 应保留交互模型，替换数据模型和完成判定。

#### 方案 B：长期推荐历史面板

参考项目：[746505972/bilibili-feed-history](https://github.com/746505972/bilibili-feed-history)。

该项目监听页面中被替换的推荐卡片，将视频卡片按单条记录保存在本地，并通过侧边面板展示历史。它更像「曾经出现过的推荐视频收藏箱」，适合长期检索，但比误触撤回更重。

其实现完全不拦截网络接口：`startObserving()` 观察 `#app/#i_cecream/main/body` 的 `removedNodes`，`checkAndSaveFeedCards()` 从被移除子树寻找视频卡片，`saveFeedCard()` 克隆单卡并按 BV 号等字段去重，`saveToStorage()` 保存 `outerHTML`。`refreshHistoryDisplay()` 在独立面板重建卡片，并移除内联事件、`script` 和 `iframe[srcdoc]`。

这证明“在节点被替换时抢救旧内容 + 独立历史面板”也是可行路径。它适合长期历史，但高频 DOM 克隆、序列化和全量存储写会产生写放大，宽泛选择器也容易误收非首页卡片。

### 3.3 推荐的 ECHO 范围

ECHO 首版采用已被方案 A 验证的**最近推荐批次**形态：

- 在原生「换一换」附近提供「上一批」和「下一批」。
- 初始状态和历史边界下，按钮应明确禁用。
- 每次原生刷新成功后记录一个批次，而不是把所有视频拆成无边界历史库。
- 按标签页会话保留最近 10 批；实现后人工验收否定了“刷新即清空”的原边界，现通过 `chrome.storage.session` 支持刷新及同标签进入视频再返回后的恢复。
- 回看历史批次时，不应被误记录成新的推荐批次。
- 历史副本只承诺展示和打开链接，不承诺原生悬浮预览、稍后再看、不感兴趣菜单、埋点或实时统计。

完整历史面板可作为后续候选，不应成为首版主体。首版优先解决「刚刚那一屏找回来」这一高频、低理解成本的任务。

2026-08-26 实测表明，首页推荐容器共有 24 个子项，但原生“换一换”只替换 10 个 `.feed-card`；后续还有直播、楼层卡片和 `.bili-video-card`。刷新前后 10 个 feed card 无重复 BV 号，但刷新后 3 个卡片没有普通 `/video/BV...` 链接。提取器必须按卡片类型建模，不能把整个首页或所有卡片等同于一个推荐批次。

ECHO 独立实现一个批次状态机：

```text
原生最新批次 -> 点击换一换前保存旧批次 -> 观察到 10 张卡片身份集合变化并稳定
             -> 保存新批次并把 currentIndex 指向末尾

上一批/下一批 -> 只改变 currentIndex -> 在 ECHO 历史层渲染结构化卡片
回到末尾     -> 关闭历史层 -> 显示始终由 B站维护的原生最新批次
```

每张卡片保存 `type`、稳定目标 URL、标题、封面 URL、作者、时长和展示统计。目标 URL 是主键；普通视频可额外提取 BV 号，番剧、直播等保留原目标 URL，不强制转换为 BV。历史视图由 ECHO 自己渲染，不保存站点 HTML，也不把副本节点插回 Vue 管理的原生列表。

批次完成不使用固定 600 ms：点击前记录旧 URL 集合，在推荐容器上安装局部 `MutationObserver`；当卡片数量达到预期、URL 集合已经变化且连续两个动画帧不再改变时提交新批次，超时则放弃本次记录并保留旧历史。

这种方案没有额外网络请求和持续存储写，内存规模可控，但维护成本仍不低：提取器、卡片类型、封面懒加载、协议相对链接、登录/未登录版、A/B 页面结构和 B站样式变化都会影响结果。“只需修复提取器”仍然是持续站点适配，不是低成本保证。

### 3.4 ECHO 实现步骤与验收门槛

B站方向已经具备 Go 依据，按以下步骤实现与验收：

1. 新增独立 `bili-feed-history/` 内容脚本，仅匹配 B站首页；复用现有 B站设置总类目，但与视频工具开关独立。
2. 先实现卡片提取器和当前批次只读调试输出，对照页面逐张验证标题、链接、封面和作者。
3. 实现按标签页隔离的 10 批历史和批次导航，通过会话存储跨刷新与同标签返回恢复，关闭标签页时清理。
4. 实现独立历史层，不替换原生 Vue 节点。点击历史卡片使用真实目标链接正常打开。
5. 登录和未登录首页各连续刷新 20 次，批次边界识别不得出现半批、混批或重复记录。
6. 普通视频、番剧、直播及非 BV 卡片按目标 URL 原样保存；无法识别链接时不记录该卡并增加诊断计数。
7. 打开/关闭历史层不影响原生“换一换”、稍后再看和不感兴趣；缩放、窗口变化、深浅主题和 SPA 重建后入口不重复注入。

### 3.5 产品边界

所谓「回退」是恢复已经在客户端展示过的推荐卡片，不是让 B 站服务端推荐算法回滚。因此：

- 返回旧批次不会撤销 B 站已经发生的推荐请求。
- 旧卡片中的实时数据可能已经过期。
- 页面刷新、关闭标签页或 B 站改版后，历史是否保留取决于最终存储策略。
- 应避免把整段未经处理的页面 HTML 长期保存，以降低兼容性、安全性和存储成本风险。

### 4.2 「公开仓库」不等于「开源许可证授权」

GitHub 仓库公开，只代表他人可以查看，并可通过 GitHub 提供的功能进行 fork。GitHub 服务条款授予的站内查看和 fork 权利，不能替代软件许可证，也不自动授予在 ECHO 中复制、修改、发布代码的权利。

没有许可证时，默认版权仍归作者所有。可以研究公开行为、讨论需求、学习一般思想和独立解决同一问题，但不应复制受版权保护的具体表达，包括源码、成套样式、文案、图标和截图。

### 4.3 MIT 与 ECHO GPL-3.0 的关系

ECHO 当前采用 GPL-3.0。MIT 许可代码通常可以并入 GPL-3.0 项目，但需要同时满足：

1. 保留 MIT 代码原有的版权声明和 MIT 许可文本。
2. 明确记录引用文件、上游仓库、作者、版本或提交，以及 ECHO 所做修改。
3. 组合后的 ECHO 发布物继续按 GPL-3.0 提供完整对应源代码。
4. 不把上游 MIT 代码错误标记为 ECHO 原创，也不删除上游归属。

由于 `zhihu-custom` 仓库没有标准 `LICENSE` 文件，虽然脚本头和 `package.json` 对 MIT 的声明已经构成明确许可证据，ECHO 仍采用更保守的做法：**不直接移植其实现；如后续确有必要复用实质性代码，先联系作者确认版权声明写法。**

## 五、实施阶段的洁净实现规则

本分支后续开发应遵守以下规则：

1. 外部项目只用于确认需求、交互形态和可行性，不把其源码复制到工作区作为起点。
2. 根据知乎/B站实际页面行为、公开网络请求和 ECHO 自身架构重新设计实现。
3. 不复用两个无许可证 B 站项目的函数结构、变量命名、成套 CSS、文案、图标或页面布局。
4. 对 `zhihu-custom` 同样优先独立实现；若出现必要引用，先在本文增加来源、提交、文件、引用范围和许可证履行清单，再写代码。
5. 在 PR 或发布说明中保留本调研文档，确保产品来源与代码来源可以区分。
6. 发布前再次检查所有新增文件，不得残留未经授权的第三方代码或资产。

## 六、建议的交付顺序

两个功能共享产品主题，并且都有公开实现证明核心路径可行。建议分阶段交付，避免同时铺开两个站点的全部边界：

1. 先实现 B站当前标签页最近 10 批：卡片提取、批次稳定判定、历史层和前后导航。
2. B站完成 20 次连续刷新验收后，接入正式独立开关；长期历史面板留待后续。
3. 知乎先把现有名单探针扩展为身份链探针，验证 `id -> author_member_hash_id` 和 `url_token -> 评论链接` 的当前站点命中情况。
4. 实现知乎阶段 A：手动同步、账号分区、推荐/关注/回答过滤与临时查看。
5. 完成阶段 A 的 100 项滚动和多账号验收后，实现阶段 B：一级评论与子评论过滤。
6. 评论阶段优先使用 DOM 作者主页路径中的稳定 ID，不默认引入 MAIN world；只有出现无作者链接的受支持评论结构时再评估桥接。
7. 两个模块均独立开关和独立失效，任何站点适配故障都不影响 ECHO 通用功能。

## 七、进入实现前的决策项

- 知乎功能正式文案是否采用“隐藏黑名单用户内容”，并明确首版覆盖推荐、关注、回答和评论。
- 知乎实验期默认关闭；完成覆盖率验收后再决定正式版本默认状态。
- 知乎只考虑设置页手动同步；自动全量校准已从当前范围排除。
- 若采用手动同步，是否接受 2,000 人约 2.5 分钟、5,000 人约 6 分钟的显式等待。
- 是否愿意承担多账号隔离；若不做，则账号变化时必须停用功能，不能继续过滤。
- 知乎首版是否包含本地补充黑名单。
- 被过滤内容是否提供「临时查看」入口。
- B站历史层只承诺展示和打开链接，不复刻悬浮预览、稍后再看和不感兴趣菜单。
- B站首版采用当前标签页 10 批；跨刷新历史和完整历史中心不在当前范围。
