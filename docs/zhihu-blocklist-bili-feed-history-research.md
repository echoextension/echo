# 知乎黑名单增强与 B 站推荐回退：产品调研与开源合规

> 调研日期：2026-08-25  
> 工作分支：`feature/zhihu-blocklist-bili-feed-history`  
> 状态：可行性与大名单基线实测完成，具体产品范围待确认
> 说明：本文记录产品判断与开源合规边界，不构成法律意见。

## 结论摘要

- **B 站推荐回退：Go。** 需求边界明确，首版采用当前标签页内的结构化批次历史，不复制参考项目，也不持久化整段页面 HTML。
- **知乎黑名单增强：技术可行。** 过滤查找本身很轻；官方名单同步是分钟级、百请求级任务，但实测没有出现错误或限流。首版采用用户手动同步，还是增加自动校准，属于产品与复杂度取舍，尚未决定。
- 2026-08-25 的匿名实测账号有 2,097 名黑名单用户。知乎接口将每页硬限制为 20 人，全量读取需要 105 次请求、约 152 秒墙钟时间和 1.15 MB 响应数据。
- **手动同步是可接受的 MVP 候选。** 用户在 ECHO 设置页主动发起，等待数分钟后保存名单，交互简单、实现范围小，也避免扩展在用户无感时发起百次请求。
- 自动定时校准、跨标签页单实例任务、原生拉黑实时增量等属于增强候选，不应在产品确认前视为首版前置条件。
- 两个功能均应独立开关和独立失效。任何站点适配故障不得影响 ECHO 的通用功能。

## 一、共同的产品命题

本轮候选功能都不是增加新的内容消费入口，而是修复中国主流网站中违背用户直觉的既有交互：

- 知乎的「屏蔽用户」没有可靠地阻止该用户的内容继续出现在推荐流、回答和评论中。
- B 站首页「换一换」是不可逆操作，误触后无法找回刚刚看到但尚未来得及打开的视频。

二者可以归纳为同一条产品方向：**把网站原本不完整或不可逆的用户控制，补成符合直觉、可预期的控制。** 这延续了 ECHO 从通用浏览器增强走向中国网站具体场景深度优化的演进。

## 二、知乎：让黑名单真正作用于内容

### 2.1 问题与预期

用户对「拉黑」的合理预期是：拉黑某个用户后，不再主动看到该用户本人发布的内容。知乎官方黑名单更偏向限制互动关系，不能稳定满足这一内容层预期。

ECHO 的目标应表述为：

> 用户在知乎拉黑某人后，ECHO 将其视为内容黑名单成员，并在支持的页面中隐藏该用户本人发布的内容。

首版建议覆盖：

1. 首页推荐流与关注流中的问题、回答、文章和想法。
2. 问题页中的回答。
3. 评论和子评论。
4. 同步知乎官方黑名单。
5. 用户在页面内新增或解除拉黑后，当前会话及时更新。

首版暂不扩大到「别人引用、回复或讨论黑名单用户」的内容。过滤对象应以内容作者为准，避免因为正文提及某个用户而误伤正常内容。

### 2.2 已有项目验证

参考项目：[liuyubing233/zhihu-custom](https://github.com/liuyubing233/zhihu-custom)（知乎修改器）。调研时用户脚本版本为 `5.21.4`，仓库仍在维护。

该项目已经验证以下能力可行：

- 从知乎接口分页同步官方黑名单。
- 以稳定的用户 ID，而不是昵称，识别黑名单成员。
- 在推荐列表、问题回答、用户主页和评论区过滤黑名单用户内容。
- 在知乎黑名单之外维护本地黑名单，并合并两类名单进行匹配。
- 监听知乎的动态页面与评论加载，在新增内容出现后继续过滤。

参考实现的同步接口为：

```text
GET https://www.zhihu.com/api/v3/settings/blocked_users?offset={offset}&limit={limit}
```

请求在 `www.zhihu.com` 登录页面内发起，通过 `credentials: "include"` 使用浏览器已有登录态；插件无需读取、复制或保存 Cookie。响应中的 `data[].id`、`data[].url_token` 和 `paging` 可分别用于稳定身份匹配与分页。新增或解除拉黑则可使用 `/api/v4/members/{url_token}/actions/block`，写操作需要 XSRF 处理，但 ECHO 首版不必主动代理原生拉黑操作。

这说明需求真实且可以实现，但不能把参考项目的“能工作”视为生产架构已经解决。尤其需要独立处理多账号缓存隔离、部分分页失败、同步期间名单变化、接口限流、主世界请求拦截风险，以及评论区 ID 表达不一致。参考项目没有明显展示完整的账号级快照隔离，ECHO 不应照搬其存储模型。

### 2.3 推荐的 ECHO 范围

ECHO 不应复制「知乎修改器」的大而全形态。建议保持单一承诺：**拉黑之后，不再看到此人本人发布的内容。**

候选首版产品行为（尚待确认）：

- 实验期默认关闭，由用户主动开启；稳定性达到验收标准后再讨论默认策略。
- 过滤后直接收起内容，不在信息流中留下大面积占位。
- 提供轻量的临时查看入口，降低误判时的不可恢复感。
- 设置页提供总开关、手动同步按钮、成员数量、最近成功时间、同步进度和错误状态；是否显示账号匿名标识取决于是否支持多账号隔离。
- 本地补充名单属于后续候选；首版可先围绕官方黑名单闭环，避免同时引入名单管理产品。

### 2.4 登录态与名单获取机制

无论采用手动还是自动触发，底层获取链路相同：

1. 知乎内容脚本通过 `/api/v4/me` 或页面 `js-initialData` 确认当前账号稳定 ID。
2. 在知乎页面的同源上下文中只读调用官方黑名单接口，浏览器自动附带当前登录态。
3. 按服务端允许的分页大小顺序拉取，响应暂存在本次任务的内存或临时存储中。
4. 每页校验结构、总数、稳定 ID 和重复项；全部完成后才生成新快照。
5. 全部完成后保存新名单；若中途失败，不应用明显不完整的结果。

#### 候选方案 A：设置页手动同步（MVP）

用户在 ECHO 设置页主动点击“同步知乎黑名单”，扩展通过已打开且已登录的知乎标签页执行分页请求，并显示“已读取人数 / 官方总数”和预计等待时间。2,097 人实测约需 2 分 32 秒；即使更大名单需要数分钟，只要进度明确、可以取消且不会阻塞正常浏览，这一成本并非不可接受。

该方案的优点是实现和行为都容易解释：不需要定时器、后台租约或自动重试策略，也不会在用户无感时产生大量请求。首版最低防错要求是同步期间禁用重复点击、失败时不覆盖已有完整名单、成功后记录数量和时间。若没有打开的知乎标签页，可以提示用户打开知乎后重试。

它的局限同样明确：用户在知乎新增或解除拉黑后，ECHO 的本地名单不会自动变化；换设备或切换知乎账号后，也需要用户重新同步。这些可以通过界面提示说明，不必自动等同为首版阻断项。

#### 候选方案 B：自动校准（增强）

在方案 A 验证过滤价值之后，可以再考虑首次启用自动同步、按周期校准、原生拉黑后的增量更新、多标签页单实例任务和账号级缓存。这能降低名单过期概率，但会显著增加状态管理、请求触发解释、异常恢复和测试范围。

当前调研只证明两种方案在技术上都有实现路径，没有证明自动方案必然优于手动方案。首版选择应由产品体验、开发投入和用户对几分钟显式等待的接受程度共同决定。

### 2.5 大名单实测方法

为避免在正式代码中凭假设设计，仓库提供独立的本地 MV3 调研扩展：

- 工具目录：`crawler/zhihu-blocklist-probe/`
- 匿名基线报告：`crawler/echo-zhihu-blocklist-probe-2026-08-25T15-14-21-424Z.json`
- 运行范围仅为 `https://www.zhihu.com/*`，只发起 GET 请求。
- 快速模式测试 `limit=20/50/100`；完整模式串行读取全部分页，请求间隔 250 ms。
- 对 `429` 和服务端错误进行有限指数退避，支持用户停止。
- 报告不含姓名、原始用户 ID、URL Token、Cookie 或响应正文；仅保留聚合指标和账号 ID 的 SHA-256 截断值。

该工具被版本控制以支持跨设备、跨账号和跨知乎版本复测，但不在 ECHO 正式 `manifest.json` 中注册，不进入生产扩展运行链路。

### 2.6 2026-08-25 实测结果

测试环境为 Windows 10/11 兼容 UA、Chrome/Edge Chromium 151 登录态，完整扫描结果如下：

| 指标 | 实测结果 |
| --- | ---: |
| `/api/v4/me` 登录态确认 | HTTP 200，72 ms |
| 官方报告总人数 | 2,097 |
| 实际唯一 `id` | 2,097 |
| 实际唯一 `url_token` | 2,097 |
| 请求 `limit=20/50/100` 的实际返回数 | 均为 20 |
| 完整分页数 | 105 |
| 正常满页 / 末页 | 104 × 20 / 1 × 17 |
| 接口累计耗时 | 126,166 ms |
| 加 250 ms 页间隔的墙钟估算 | 152,166 ms（约 2 分 32 秒） |
| 总响应体积 | 1,145,645 字节（约 1.09 MiB） |
| 单页平均 / P95 / 最大耗时 | 1,201.6 / 1,294 / 1,778 ms |
| 重复 ID / 缺失 ID | 0 / 0 |
| 重试或限流 | 0 |
| 所有分页的 `paging.totals` | 始终为 2,097 |

结论：接口可以取回官方后台 UI 无法完整展示的全部名单，数据在本次静态扫描中完整一致；但每页 20 人是服务端硬限制，客户端不能通过提高 `limit` 降低请求数。按相同速度估算，5,000 人约需 250 个请求和 6 分钟。末页虽然 `paging.is_end=true`，仍存在 `paging.next`，因此正式实现必须以 `is_end` 为主要终止依据，并用计数和最大页数作为防御性约束。

一次成功扫描不能证明长期不会限流，也不能覆盖扫描期间名单发生增删的情况。该结果支持“可实现”；同时更支持由用户显式、低频触发，而不是每次打开知乎都全量同步。

### 2.7 同步复杂度的分层选择

首版不必预设完整自动状态机。可以按产品选择分为三层：

| 层级 | 能力 | 复杂度判断 |
| --- | --- | --- |
| MVP 必要 | 设置页手动触发、串行分页、显示进度、禁止并发点击、完整成功后保存、失败不覆盖旧名单 | 范围明确，建议首版评估 |
| 稳健增强 | 账号隔离、临时快照与严格总数校验、取消后恢复、跨标签页结果通知 | 对多账号和异常场景有价值，可随首版风险取舍 |
| 自动化增强 | 周期校准、单实例租约、随机抖动、原生拉黑增量更新、失败退避 | 非首版必需，待手动方案验证价值后决定 |

即使选择最小手动方案，也建议保留以下低成本保护：

- 同一次手动同步只运行一个任务，重复点击不重复发起请求。
- 只有到达 `is_end=true` 且唯一人数与 `totals` 一致时才保存新名单。
- 任一分页失败时保留上次成功名单，并向用户显示失败位置。
- 设置最大页数、总任务时限和有限重试，防止异常分页无限运行。

以下问题可以作为增强项，而不是默认写入首版范围：

- **账号隔离：** 若要支持同一浏览器切换多个知乎账号，缓存键应包含稳定账号 ID；若首版仅面向单账号，则至少在同步时记录账号并在使用前校验。
- **跨标签页单实例：** 自动同步时价值较高；设置页单按钮触发时，禁用按钮通常已经足够。
- **并发变更校验：** `offset` 分页期间发生增删可能漂移，可在结束后复查总数或第一页；是否首版实现取决于实测发生概率和额外请求成本。
- **自动校准：** 例如 7 天周期和失败退避，只是候选参数，未形成产品决定。

黑名单属于账号关系数据，只应存入 `chrome.storage.local`，不应放入 `chrome.storage.sync`。`sync` 区总量和单项配额较小，还会跨设备上传；这里只适合保存功能开关和同步周期。正式发布前必须同步更新隐私政策，明确 ECHO 会在本地处理知乎账号标识、黑名单关系和页面作者标识，但不会上传这些数据。

### 2.8 过滤机制与性能预算

加载成功快照后，在每个知乎顶层页面构建两个内存集合：

```text
blockedIds: Set<stable-user-id>
blockedUrlTokens: Set<people-url-token>
```

推荐流和回答通常可从卡片的结构化属性或接口数据取得稳定作者 ID；评论 DOM 可能只暴露 `/people/{url_token}`，因此两种索引都必要。昵称不稳定且可能重复，绝不能作为匹配键。推荐卡片同时出现问题作者和回答作者时，应匹配当前实际展示内容的作者；评论的回复对象命中黑名单时，不应删除非黑名单作者的评论。

名单规模不是主要性能瓶颈。构建索引为 $O(N)$，卡片匹配近似 $O(1)$；2,097 人甚至更大名单对 `Set.has()` 的成本很低。实际风险来自 DOM 查询、JSON 属性解析、全页重复扫描和多个观察器。

实现约束：

- 只观察信息流、回答列表和已打开评论容器，不观察整个 `document.body` 后反复全页扫描。
- 只处理 MutationObserver 的 `addedNodes`，使用 `requestAnimationFrame` 合并同一帧变更。
- 用 `WeakSet` 或私有属性标记已处理节点；设置变化时才显式重新评估。
- 每个页面初始化时读取一次快照，禁止每张卡片调用 `chrome.storage`。
- 选择器、JSON 或作者标识解析失败时放过内容并记录本地诊断计数，避免误伤。
- 首版采用 CSS 类隐藏和轻量“临时查看”，不要用 `innerHTML` 重写知乎内容。

建议性能验收基线：初始 100 张卡片过滤不产生超过 50 ms 的单个长任务；每批 20 个新增节点处理目标低于 16 ms，最迟下一帧完成；关闭功能后不保留站点观察器；正常浏览期间不产生轮询网络请求。

### 2.9 尚待实测的问题

- 未登录、Cookie 过期、验证码、风控和不同知乎页面版本下的失败响应。
- 扫描期间新增或解除拉黑时，`offset` 分页是否出现重复或漏项。
- 连续多次完整扫描、更多设备和 5,000 人以上账号是否触发限流。
- 同一浏览器切换知乎账号时，账号检测与缓存隔离是否及时可靠。
- 推荐流中问题作者与回答作者同时存在时，应以当前卡片实际展示内容的作者为准。
- 评论回复对象命中黑名单时，不应误删非黑名单作者的评论。
- 知乎在页面内拉黑后，能否稳定捕获状态变化并立即过滤。
- 官方黑名单实际数量上限，以及 ECHO 是否有必要提供本地名单兜底。

## 三、B 站：让「换一换」可以回退

### 3.1 问题与预期

用户点击 B 站首页「换一换」后，上一批推荐立即消失。误触或操作过快时，用户无法找回刚扫到的感兴趣视频。

核心需求不是建立一个新的观看历史中心，而是：

> 点击「换一换」之后，可以立即回到上一批推荐，并能在已经浏览过的批次间前进和后退。

### 3.2 已有项目验证

#### 方案 A：按批次前进和后退

参考项目：[qiweiii/bili-feed-history](https://github.com/qiweiii/bili-feed-history)。

该项目在「换一换」附近增加前进、后退按钮，以批次保存当前推荐卡片，最多保留最近 10 批，并把选中的历史批次重新显示在首页推荐区域。该形态与本需求最贴合。

其实现通过点击“换一换”后固定等待约 600 ms，再克隆 `.feed-card` 并把整批 `innerHTML` 写入本地存储。它验证了批次前进/后退的交互价值，但固定延时在慢网或渐进更新时可能记录半批内容；克隆 HTML 也不包含原 Vue 组件状态和事件，不能作为 ECHO 的技术方案。

#### 方案 B：长期推荐历史面板

参考项目：[746505972/bilibili-feed-history](https://github.com/746505972/bilibili-feed-history)。

该项目监听页面中被替换的推荐卡片，将视频卡片按单条记录保存在本地，并通过侧边面板展示历史。它更像「曾经出现过的推荐视频收藏箱」，适合长期检索，但比误触撤回更重。

其实现观察较大的页面子树，扫描被移除节点，按 BV 号等字段去重，并将卡片 HTML 写入 `chrome.storage.local`；默认上限可达 1,000 条。该方案证明长期历史面板可行，但高频 DOM 克隆、序列化和全量存储写会产生写放大，宽泛选择器也容易误收非首页卡片。

### 3.3 推荐的 ECHO 范围

首版建议采用方案 A 的产品形态，但进行 ECHO 自己的交互设计与独立实现：

- 在原生「换一换」附近提供「上一批」和「下一批」。
- 初始状态和历史边界下，按钮应明确禁用。
- 每次原生刷新成功后记录一个批次，而不是把所有视频拆成无边界历史库。
- 仅保留当前标签页最近 10 批，首版不跨刷新持久化。
- 回看历史批次时，不应被误记录成新的推荐批次。
- 用户从历史批次点击视频时，应保持原视频链接可正常打开。

完整历史面板可作为后续候选，不应成为首版主体。首版优先解决「刚刚那一屏找回来」这一高频、低理解成本的任务。

技术上应在原生刷新动作前记录当前批次，再通过推荐容器上的局部观察器等待新批次稳定。每张卡片只保留 BV 号、标题、链接、封面 URL、UP 主、时长和展示统计等必要字段；历史视图由 ECHO 自己渲染，不把站点 HTML 当成持久化 API，也不伪造 B 站 Vue 节点。回到最新批次时移除历史视图，继续显示原生推荐。

这样首版没有额外网络请求和持续存储写，最多约百余条结构化卡片，内存与 CPU 成本可控。页面改版时只需修复提取器和轻量渲染器，不需要兼容历史 HTML 快照。

### 3.4 产品边界

所谓「回退」是恢复已经在客户端展示过的推荐卡片，不是让 B 站服务端推荐算法回滚。因此：

- 返回旧批次不会撤销 B 站已经发生的推荐请求。
- 旧卡片中的实时数据可能已经过期。
- 页面刷新、关闭标签页或 B 站改版后，历史是否保留取决于最终存储策略。
- 应避免把整段未经处理的页面 HTML 长期保存，以降低兼容性、安全性和存储成本风险。

### 4.2 「公开仓库」不等于「开源许可证授权」

GitHub 仓库公开，只代表他人可以查看，并可通过 GitHub 提供的功能进行 fork。GitHub 服务条款授予的站内查看和 fork 权利，不能替代软件许可证，也不自动授予在 ECHO 中复制、修改、发布代码的权利。

没有许可证时，默认版权仍归作者所有。可以研究公开行为、讨论需求、学习一般思想和独立解决同一问题，但不应复制受版权保护的具体表达，包括源码、成套样式、文案、图标和截图。

### 4.3 MIT 与 ECHO GPL-3.0 的关系

ECHO 当前采用 GPL-3.0。MIT 许可代码通常可以并入 GPL-3.0 项目，但需要同时满足：

1. 保留 MIT 代码原有的版权声明和 MIT 许可文本。
2. 明确记录引用文件、上游仓库、作者、版本或提交，以及 ECHO 所做修改。
3. 组合后的 ECHO 发布物继续按 GPL-3.0 提供完整对应源代码。
4. 不把上游 MIT 代码错误标记为 ECHO 原创，也不删除上游归属。

由于 `zhihu-custom` 仓库没有标准 `LICENSE` 文件，虽然脚本头和 `package.json` 对 MIT 的声明已经构成明确许可证据，ECHO 仍采用更保守的做法：**不直接移植其实现；如后续确有必要复用实质性代码，先联系作者确认版权声明写法。**

## 五、实施阶段的洁净实现规则

本分支后续开发应遵守以下规则：

1. 外部项目只用于确认需求、交互形态和可行性，不把其源码复制到工作区作为起点。
2. 根据知乎/B站实际页面行为、公开网络请求和 ECHO 自身架构重新设计实现。
3. 不复用两个无许可证 B 站项目的函数结构、变量命名、成套 CSS、文案、图标或页面布局。
4. 对 `zhihu-custom` 同样优先独立实现；若出现必要引用，先在本文增加来源、提交、文件、引用范围和许可证履行清单，再写代码。
5. 在 PR 或发布说明中保留本调研文档，确保产品来源与代码来源可以区分。
6. 发布前再次检查所有新增文件，不得残留未经授权的第三方代码或资产。

## 六、建议的交付顺序

两个功能共享产品主题，但站点依赖和验证方式不同，建议在同一分支中分阶段交付：

1. 先完成 B 站推荐批次回退。需求边界清晰，可快速验证交互价值。
2. 确认知乎首版采用手动同步 MVP，还是同时加入部分稳健增强。
3. 若采用手动 MVP，实现设置页触发、同步进度、完整性校验和本地保存，再接入首页/回答过滤。
4. 根据首版反馈决定是否继续验证并实现多账号、自动校准和原生拉黑增量更新。
5. 评论区动态过滤最后单独评估，并针对不同页面版本做回归验证。
6. 两个模块均提供独立开关，任何一个站点适配失败都不影响 ECHO 的通用功能。

## 七、进入实现前的决策项

- 知乎增强是否默认开启，还是默认关闭并由用户主动启用。
- 知乎首版选择设置页手动同步，还是加入自动校准；当前文档不预设答案。
- 若采用手动同步，是否接受 2,000 人约 2.5 分钟、5,000 人约 6 分钟的显式等待。
- 首版是否支持同一浏览器多个知乎账号，还是先限定单账号并明确提示。
- 知乎首版是否包含本地补充黑名单。
- 被过滤内容是否提供「临时查看」入口。
- 若后续增加自动校准，再决定周期和失败退避上限。
- B 站首版采用当前标签页 10 批；跨刷新历史留作后续决策。
