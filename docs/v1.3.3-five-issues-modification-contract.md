> 制定日期：2026-08-30  
> 适用分支：`feature/zhihu-blocklist-bili-feed-history`

## 1. 契约目的

本文只约束以下五项已经明确提出的问题：

1. 设置页两个 B站功能的介绍文案过于简陋。
2. 设置页右侧内容滚动时，左侧导航的跟随定位不稳定。
3. FRE1 网站增强横条的交互暗示与实际行为不一致，以及 FRE1、FRE2 主按钮箭头偏离既有设计。
4. 设置页知乎黑名单开关、授权确认、首次同步和后续手动同步之间缺少正确联动。
5. NTP 热搜榜包含两个必然达不到显示门槛的类别，并且新安装用户的默认值需要改为关闭，同时不得改变升级用户现状。

本文的核心原则是：**只修正上述问题，不借机重构无关模块，不增加未经确认的新功能，不改变未被点名的产品行为。**

若实际编码过程中发现本文没有覆盖、且无法通过现有约束唯一决定的产品问题，必须暂停该部分修改并重新确认，不得自行选择产品方案。

## 3. 问题一：设置页两个 B站功能文案

### 3.1 问题定义

当前设置页对“B站视频优化工具”和“B站推荐回退”各只保留一句概括，虽然简短，但没有充分说明实际能力和边界。主干旧文案信息较完整，却存在三段话啰嗦、emoji 难看和重点不清的问题。

本轮目标不是恢复旧文案，而是在简洁与完整之间重新整理信息。

### 3.2 B站视频优化工具文案必须说明

文案应采用简洁、结构化表达，并准确覆盖：

- 功能出现在 Bilibili 视频播放页左侧悬浮工具中。
- 支持画面反色和 RGB 通道交换。
- 支持旋转、镜像，以及旋转后的适应/填充与画面位置调整。
- 支持 `0.25×` 超慢速和 `3×` 极速两个扩展倍速档位。
- 各项能力可以组合使用，并可恢复或关闭。

### 3.3 B站推荐回退文案必须说明

文案应准确覆盖：

- 功能针对 B站首页推荐区域和原生“换一换”行为。
- 原生“换一换”后记录推荐批次。
- 支持上一批和下一批导航。
- 每个标签页会话最多保留最近 10 批。
- 刷新首页或同标签进入视频再返回时，可以恢复当前标签页会话中的批次。
- 关闭标签页或关闭该功能后清除对应会话历史。

### 3.4 文案表达约束

- 不使用装饰性 emoji。
- 不写成大段营销话术。
- 不出现“任意倍速”；实际只有明确的扩展档位。
- 不承诺跨标签页、跨浏览器重启或跨设备保存推荐历史。
- 不暗示恢复整个 B站页面状态；功能恢复的是已记录的推荐卡片批次。
- 不暗示所有 B站页面都支持推荐回退。
- 设置页和 FRE2 对相同能力的说法必须一致，但不要求逐字相同。

### 3.5 验收标准

- 用户无需查 README 即可从设置页理解两个功能分别做什么、在哪里生效、关键能力是什么、数据保留到什么时候。
- 信息量明显高于当前一句话，但显著短于主干旧版的三段式说明。
- 浅色、深色和窄窗口下新增文案不遮挡开关，不破坏现有演示布局。

## 4. 问题二：设置页左侧导航随滚动定位

### 4.1 产品边界

左侧导航继续只保留现有五项：

1. 效率操作
2. 页面体验
3. 标签页管理
4. 个性化
5. 备份与恢复

**不得新增其他导航项。**

### 4.2 已确认的技术问题

- `initScrollNav()` 当前被两个 `DOMContentLoaded` 入口重复调用，形成两套点击监听和两套观察逻辑。
- 当前 IntersectionObserver 只在视口上部一条较窄区域中判定，快速滚动、短分区、分区间距和页面底部都可能错过。
- 同一批 observer entries 被逐个处理，最终高亮依赖回调条目顺序，不是确定的页面顺序。
- 点击左侧导航后虽然立即高亮目标，但平滑滚动途中 observer 可能重新高亮经过的栏目。
- hash 初始化与点击导航使用不同定位方式，容易造成初始抖动或位置不一致。

### 4.3 必须实施的行为

- 整个设置页只能初始化一套滚动导航逻辑。
- Scroll spy 只观察或计算左侧五个导航项对应的五个正文 section，明确排除 `labSection`。
- 改为确定性定位规则：根据固定激活线，选择顶部已经越过该激活线的最后一个有效导航 section。
- 在第一个 section 尚未越过激活线时，高亮第一项。
- 滚动到页面底部时，高亮稳定保持“备份与恢复”。
- 使用 `requestAnimationFrame` 或等效方式节流滚动计算，避免连续滚动时反复抖动。
- 左侧点击必须继续准确滚动到对应正文位置。
- 程序化平滑滚动期间，经过的中间 section 不得抢占用户刚点击的目标高亮。
- 用户主动中断平滑滚动时，应及时恢复按实际位置定位，不能长期锁定错误栏目。
- 页面初始 hash、左侧点击和手动滚动应共用同一套偏移和激活规则。

### 4.4 坐标和布局约束

实现时必须考虑：

- 设置页自身 CSS 缩放。
- 动态书签栏高度。
- 子选项显示或隐藏造成的正文高度变化。
- 窗口 resize。
- 最后一项正文较短、无法自然移动到视口顶部的情况。

不得继续依赖一个固定 `48px` 偏移解决所有情况，也不得只在页面加载时缓存一次 section 坐标后永久使用。

### 4.5 验收标准

以下场景中，五项导航必须按正文位置连续、稳定切换，不跳过、不滞后、不来回闪烁：

- 鼠标滚轮慢速滚动。
- 快速滚动。
- 触控板惯性滚动。
- 拖动浏览器滚动条。
- 从顶部直接滚到底部，再从底部返回顶部。
- 逐个点击左侧五项。
- 点击后立刻反向滚动。
- 带有效 section hash 打开设置页。
- 页面缩放或窗口尺寸变化后继续滚动。
- 滚动到页面底部。

## 5. 问题三：FRE 横条与主按钮箭头

### 5.1 FRE1 网站增强横条

当前横条右侧箭头在 hover 时移动并改变背景，视觉上明确暗示可以点击，但横条实际是普通 `div`，不能点击，也不能通过键盘进入 FRE2。

本轮选择：**将整条横条改为真正可访问的 FRE2 导航入口。**

必须满足：

- 点击横条任意非空区域均进入 FRE2。
- 使用真实链接语义，不只给箭头加点击事件。
- 可通过 Tab 聚焦，通过 Enter 激活。
- 有清晰的 `:focus-visible` 状态。
- hover、focus 和可点击语义一致。
- 不在横条内部嵌套其他交互元素。
- 保持现有文案和展示内容，除非为链接语义做最小必要调整。

### 5.2 FRE1、FRE2 主按钮箭头

当前两页为主按钮箭头额外增加了圆形边框、圆形背景和内阴影，偏离原来简洁的 FRE 按钮语言。

本轮必须：

- 移除箭头外层的圆圈、边框、背景和阴影。
- 使用普通行内 SVG 箭头。
- FRE1 与 FRE2 的箭头尺寸、线宽、文字间距和 hover 位移保持一致。
- 箭头只做轻微水平位移，不增加新的夸张动画。
- 在 `prefers-reduced-motion` 下关闭位移动画。
- 清理仅为圆形箭头服务的无效宽高和媒体查询规则。

### 5.3 修改边界

- 不改变 FRE1、FRE2 的目标页面。
- 不改变右上角步骤导航。
- 不改变 FRE3、FRE4 的产品流程。
- 不借机重做所有 CTA 文案或按钮造型。
- 可以复用现有标准样式，但不得为此进行超出必要范围的全站样式重构。

### 5.4 验收标准

- FRE1 横条的视觉暗示和实际行为一致。
- 鼠标和键盘均能通过横条进入 FRE2。

## 6. 问题四：知乎黑名单开关、授权与同步状态机

### 6.1 核心产品规则

- 知乎功能开关始终可见。
- 没有完成过一次有效同步时，开关不能持久化为开启。
- 用户第一次尝试开启时，必须先看到明确授权提示。
- 用户确认后，立即进入现有知乎授权/登录页面连接与同步流程。
- 用户取消授权、取消同步、未登录、同步失败或连接中断时，开关仍保持关闭。
- 只有完成一次完整同步并保存有效快照后，开关才能变为开启。
- 官方黑名单为 0 人也是一次有效完整同步，必须允许开关开启。
- 从未授权时，下方同步操作行隐藏；用户确认授权并开始任务后，该操作行成为唯一的同步状态和操作位置。
- 同步准备、同步进度、取消、失败、成功和后续手动更新必须复用同一操作行，按钮不得在主开关行与操作行之间跳动。
- 主开关行始终只显示固定功能说明和右侧开关，不插入同步状态或取消按钮。

### 6.2 授权弹层契约

知乎授权提示必须使用设置页既有的确认弹层视觉和交互框架：

- 同一层级的 overlay。
- 同一 modal 容器尺寸和布局。
- 同一入场、退场动画。
- 同一标题区、图标区、内容区、风险说明区和按钮区结构。
- 同一取消按钮与确认按钮样式。
- 同一深色模式表现。
- 同一关闭和事件清理机制。

这应通过参数化复用同一 modal 控制器或等效的单一实现完成，不允许复制出一套“看起来差不多”的知乎专用样式。

知乎弹层内容必须明确说明：

- ECHO 将连接用户已登录的知乎页面。
- ECHO 将读取知乎官方黑名单。
- 本地快照保存用于匹配的稳定账号标识、同步时间和人数等必要数据。
- 名单只保存在当前设备的扩展本地存储中。
- 名单不进入浏览器同步、不进入 ECHO 备份、不发送给 ECHO 或第三方服务。
- 用户确认后将直接开始同步。

本轮不得自行扩展 AI 弹层的产品行为。若为了共同控制器而整理代码，AI 弹层的现有可见行为必须保持不变。

### 6.3 明确状态机

#### 状态 A：关闭、无有效快照

- 开关显示为关闭。
- 手动同步区域隐藏。
- 点击开启进入状态 B，不得先写入 `true`。

#### 状态 B：等待用户授权

- 开关仍显示为关闭。
- 显示授权弹层。
- 取消后返回状态 A。
- 确认后进入状态 C。

#### 状态 C：首次同步中

- 后台创建独立知乎窗口，并在窗口中显示 ECHO 提示浮层；不借用用户正在浏览的知乎标签页。
- 浮层文案明确说明 ECHO 正在读取知乎官方黑名单、进度请在 ECHO 设置页查看、完成前不要关闭窗口，完成后窗口自动关闭。
- 浮层阻止用户误点击页面内容导致同步页面导航；未登录时应明确失败并提示用户先登录知乎后重新开始，不保存部分结果。
- 开关仍未持久化为 `true`。
- 下方固定同步操作行显示连接、进度和取消反馈，操作按钮始终位于该行右侧。
- 禁止重复启动第二个同步任务。
- 关闭设置页只会断开界面订阅，不会取消仍在独立窗口中运行的任务。
- 重新打开设置页后，只重新连接并显示仍在运行的任务及当前进度；这不是断点续传。

#### 状态 D：首次同步完整成功

必须同时满足：

- 收到同步完成结果。
- 本地快照对象存在。
- `records` 是数组；允许为空数组。
- 同步时间、账号和快照结构有效。

满足后：

- 写入 `zhihuBlocklistFilter: true`。
- 开关显示为开启。
- 显示“已同步 N 人”和时间。
- 显示后续手动更新同步区域。

#### 状态 E：首次同步失败或取消

包括授权取消、用户取消同步、未登录、接口失败、超时、独立知乎窗口被关闭或内部连接断开：

- 不写入 `true`。
- 开关恢复或保持关闭。
- 未授权取消时同步操作行隐藏；已经开始任务后失败或取消时，同一操作行保留明确原因和重新同步入口。
- 不保存部分抓取结果为有效快照。
- 单纯关闭设置页不属于任务失败；任务继续运行。

#### 状态 F：已有有效快照且功能关闭

- 开关显示为关闭。
- 有效快照仍保留在本地，不因关闭功能而删除。
- 手动更新区域可以继续显示，因为用户已经完成过授权和有效同步。
- 用户再次开启时可直接启用已有有效快照，不强制再次同步或再次授权。

#### 状态 G：已有有效快照且功能开启

- 开关显示为开启。
- 手动更新区域显示。
- 手动更新成功后原子替换旧快照。
- 手动更新失败或取消时保留旧有效快照，并保持原来的开启状态。

### 6.4 零名单规则

`records: []` 且同步流程完整成功时，代表“已确认该账号当前官方黑名单为 0 人”，不是“从未同步”。

因此必须修正过滤端以 `Array.isArray(records)` 等结构条件判断有效快照，不能再以 `records.length > 0` 作为有效性条件。

零名单时：

- 开关可以开启。
- 设置页显示“已同步 0 人”和时间。
- 手动更新区域显示。
- 知乎页面不应误过滤任何内容。
- 不要求为了空集合启动没有意义的重型 DOM 扫描，但“同步有效状态”必须成立。

### 6.5 旧版本和跨设备兼容

- 旧版本中开关为开启、当前设备却没有有效本地快照：规范化为关闭。
- 开关通过 `storage.sync` 到达另一设备，但该设备没有本地快照：保持关闭。
- 旧版本已开启且当前设备已有有效快照：保持开启，不强制再次授权或同步。
- 旧版本已有有效快照但开关关闭：保持关闭，快照保留。
- 不删除用户已有有效快照。

### 6.6 并发与生命周期约束

必须处理：

- 双击确认。
- 快速连续点击开关。
- 同步进行中再次点击同步。
- 设置页关闭后任务继续，重新打开后恢复显示仍在运行的实时进度。
- 独立知乎窗口被关闭或发生导航时明确中断。
- `complete` 消息和 port 断开先后顺序。
- 同步期间知乎账号发生变化。
- 成功保存快照但开关写入失败。

不得因为竞态留下“开关开启但没有有效快照”或同时存在两个同步任务。

本轮明确不做断点续传：

- 不保存分页断点或部分名单。
- 不从中断位置恢复。
- 浏览器重启、扩展重载、独立知乎窗口关闭或同步执行上下文消失时，本次任务失败，用户只能从头重新同步。
- “重新打开设置页恢复进度”仅指重新订阅一个从未中断、仍在运行的任务。

### 6.7 验收标准

至少覆盖：

- 无快照时取消授权。
- 无快照时确认授权但未登录。
- 首次同步非空名单成功。
- 首次同步 0 人成功。
- 首次同步中取消。
- 首次同步中关闭设置页，任务继续；重新打开设置页后显示当前实时进度。
- 同步期间在用户自己的知乎标签页中浏览和跳转，任务不受影响。
- 独立知乎窗口被关闭或导航后任务明确失败，并提供从头重新同步入口。
- 浏览器重启或扩展重载后不续传未完成任务。
- 已有有效快照后关闭、再开启。
- 已有有效快照时手动更新成功、失败和取消。
- 旧版伪开启状态升级规范化。
- 跨设备只有开关、没有本地快照。

## 7. 问题五：NTP 热搜类别与默认关闭

### 7.1 类别调整

当前热搜显示门槛为 20 条。2026-08-30 对当前百度接口实测：

- `movie`（电影榜）返回 10 条。
- `teleplay`（剧集榜）返回 10 条。

两者必然无法通过现有门槛，因此必须从静态类别配置中移除，不再显示圆点，不再参与箭头、滚轮切换，也不再为它们发起无意义的首次请求。

其他类别继续保留。通用的“运行时返回不足 20 条则动态禁用”机制继续保留，用于应对其他类别临时数据不足。

### 7.2 新安装默认关闭

“默认关闭”只适用于本次修改发布之后的全新安装用户：

- 新安装时显式写入 `echo_ntp_trending: false`。
- 首次打开 NTP 即显示为关闭。
- 刷新 NTP 或重启浏览器后仍为关闭。

### 7.3 升级用户必须保持原状

升级不得改变已有用户状态：

- 之前显式开启：升级后仍开启。
- 之前显式关闭：升级后仍关闭。
- 之前从未操作、依赖旧版本“缺 key 即默认开启”：升级后仍开启。

由于“旧用户从未写 key”和“全新安装”都可能没有该 key，不能简单把 NTP 运行时的缺省解释改成关闭。

必须采用安装原因区分：

- `runtime.onInstalled` 的 `reason === 'install'`：显式写入 `false`。
- `reason === 'update'`：不补写、不覆盖该 key。
- NTP 运行时继续把缺 key 解释为旧默认开启，以保护升级用户。

`chrome.storage.local` 是最终真值；页面 `localStorage` 只用于首帧布局缓存，不得反向覆盖最终设置。

### 7.4 首帧要求

新安装用户第一次打开 NTP 时，不应明显出现热搜先显示、随后关闭的闪烁。

为满足此要求，可以对静态 `checked`、首帧 class 或初始化顺序做最小必要调整，但不得改变升级用户最终状态，也不得把 `localStorage` 提升为真实设置来源。

### 7.5 已保存类别兼容

当前类别偏好保存为数字数组索引。删除 `movie` 和 `teleplay` 后，如果继续直接解释旧数字，会导致小说、汽车、短剧错位或越界。

必须将类别持久化迁移为稳定的 `tab` 字符串：

- 新写入值使用 `realtime`、`livelihood`、`finance`、`sports`、`games`、`novel`、`car`、`drama` 等稳定标识。
- 读取旧数字时，先按照旧完整类别顺序还原原类别。
- 旧值对应 `movie` 或 `teleplay` 时，回退到 `realtime`。
- 旧值对应 `novel`、`car`、`drama` 时，必须保持原类别，不得因新数组缩短而错位。
- 越界、损坏或未知值统一回退到 `realtime`。
- 成功解析后回写稳定字符串，完成一次性迁移。

旧电影榜、剧集榜缓存可以保留为无害旧数据，也可以在直接相关的迁移中清理；不得为清理缓存扩大修改范围。

### 7.6 验收标准

- 全新安装默认关闭，且无首帧明显闪烁。
- 旧用户显式开启、显式关闭和从未写 key 三类状态均保持。
- 电影榜、剧集榜不出现在任何切换入口或切换序列中。
- 旧小说、汽车、短剧索引迁移后仍对应原类别。
- 损坏类别值安全回退热搜榜。
- 其他类别临时不足 20 条时，原有动态禁用兜底仍有效。
- 快速点击箭头或连续滚轮切换时，标题、圆点和列表保持一致。
