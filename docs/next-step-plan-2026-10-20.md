## 1. 修复有序插入标签时的状态未写回问题

### 现状

`background/tab-coordinator.js` 在处理浏览器创建的新标签时，某个分支会创建新的局部插入状态，但没有把它写回 `insertStateByWindow`。

默认的 `newest` 排序不依赖累计插入数量，因此通常不受影响。用户选择 `ordered` 后，如果 Service Worker 的内存状态已经因休眠而丢失，再从同一页面连续中键打开多个后台标签，后续标签可能反复插入同一个位置，最终顺序与打开顺序相反。

当前自动化复现已经确认：初始为 `A | B`，无预先激活事件，依次后台打开链接 1、2，实际得到 `A | 2 | 1 | B`；先发出 A 的激活事件则得到预期顺序。这是具有现实触发条件的功能缺陷，不再归为纯写法隐患。Worker 启动本身不会让已有活动标签重新发出激活事件。

### 当前代码链路

涉及文件：`background/tab-coordinator.js`。

1. `handleTabCreated()` 从 `getInsertState(tab.windowId)` 取得当前窗口状态，并把当时的 `baseTabId` 作为快照交给 `queueCreatedTab()`。
2. `queueCreatedTab()` 按窗口串行调用 `handleNewTabCreated()`，这层队列本身能够避免多个创建事件并发修改顺序。
3. `handleNewTabCreated()` 在当前基准与 `tab.openerTabId` 不一致时执行：

   ```js
   state = { baseTabId: effectiveBaseTabId, baseTabIndex, insertCount: 0 };
   ```

   这里替换的只是局部变量 `state`，没有修改 `insertStateByWindow` 中原来的对象，也没有把新对象放回 Map。
4. 标签移动完成后，函数重新通过 `getInsertState(windowId)` 取得 `globalState`，只有 `globalState.baseTabId === state.baseTabId` 时才增加 `insertCount`。在上述分支中，Map 内仍可能是空基准，因此计数不会增加。
5. 下一次后台标签创建时，代码再次从未更新的 Map 状态开始计算，可能继续使用相同的目标位置。

`handleTabActivated()` 会在标签激活时重建基准，因此前台打开或随后切换标签可能掩盖问题；但连续中键打开后台标签不会激活新标签。Service Worker 重启后 `insertStateByWindow` 为空，使这条路径具有现实触发条件。

### 预期行为示例

基准排列为 `A | B`，用户停留在 A，并在 `ordered` 模式下依次中键打开链接 1、2、3：

- 预期：`A | 1 | 2 | 3 | B`；
- 缺陷路径可能得到：`A | 3 | 2 | 1 | B`。

在 `newest` 模式下，`A | 3 | 2 | 1 | B` 本来就是预期结果，因此不能只用默认配置验证修复。

### 计划

1. 让新的基准标签、基准位置和 `insertCount` 始终写回窗口级状态。优先考虑修改 Map 中现有对象的属性，避免同一函数内同时存在“Map 对象引用”和“脱离 Map 的局部对象”；如果选择替换对象，则必须明确执行 `insertStateByWindow.set(windowId, state)`。
2. 保持 `newest` 与 `ordered` 两种既有产品语义不变。
3. 增加贴近真实浏览器事件的回归测试，测试标签必须带 `openerTabId`。
4. 覆盖“全新 Service Worker 状态下连续打开多个后台标签”的场景，不能依赖预先触发标签激活事件来初始化状态。

### 测试落点

主要测试文件：`tests/background/background.characterization.test.js`；浏览器模拟位于 `tests/helpers/fake-chrome.js`。

现有“keeps rapid ordered background tabs in creation order”测试调用 `chrome.tabs.create()` 时没有提供 `openerTabId`，因而会通过查询活动标签的兜底路径直接修改 Map 内对象，没有覆盖缺陷分支。补充测试时至少应做到：

- 初始窗口包含活动标签 A 和右侧标签 B；
- 设置 `newTabOrder: 'ordered'`；
- 不预先触发 `tabs.onActivated` 来建立插入状态；
- 连续创建三个 `active: false` 且 `openerTabId: A.id` 的标签；
- 等待窗口创建队列完成后，断言顺序为 `A、1、2、3、B`；
- 另以 `newest` 配置断言顺序仍为 `A、3、2、1、B`。

### 验收标准

- `ordered`：连续打开的后台标签保持 `1、2、3` 的创建顺序。
- `newest`：最新打开的标签仍然最靠近基准标签。
- 模拟全新 Worker 状态的回归必须通过；真实浏览器主动终止并重新唤醒 Worker 后再验证同一行为，分别记录证据，二者均通过后才声明重启场景完成验收。
- 扩展主动创建标签、加号新标签和标签关闭后的行为不发生回归。

## 2. 修复头条热搜标题解析错误及属性注入

### 现状

`search-box/trending-controller.js` 将头条接口返回的标题转义后拼入 `innerHTML`。当前转义方式适合文本节点，但没有覆盖双引号属性上下文，因此异常或恶意标题可以破坏 `data-query`、`title` 等属性结构。

普通标题中的双引号已经能够截断查询词和提示属性，这是无需恶意载荷的功能缺陷。构造的标题还可注入事件属性：在没有严格 CSP 的受控页面中，系统 Edge 已验证事件执行及父页面 DOM 访问；使用 `script-src 'self'` 时，事件执行被阻止，但属性注入和查询词截断仍然发生。

不能将普通引号等同于 XSS，也不能仅因数据来自公开接口就断言攻击概率低。现实利用还依赖能够影响标题、用户开启悬浮搜索热搜（默认关闭）、事件触发和页面 CSP 等条件。本次没有证明真实热榜已被攻击，也没有估算攻击概率。

### 当前代码链路

涉及文件：`search-box/trending-controller.js`，主要函数为 `escapeHtml()`、`renderVisibleWords()` 和 `fetchToutiaoTrends()`。

1. `fetchToutiaoTrends()` 通过后台代理读取头条公开接口，把每一项规范化为 `{ title: item.Title || '' }`，但不会也不应该假定标题符合 HTML 属性语法。
2. `escapeHtml()` 通过临时 `div` 的 `textContent`/`innerHTML` 做文本转义。这会处理 `&`、`<`、`>`，但文本节点中的双引号不需要转义，所以结果仍可包含 `"`。
3. `renderVisibleWords()` 把同一个结果同时放入元素文本和双引号属性：

   ```js
   data-query="${escapeHtml(item.title)}"
   title="${escapeHtml(item.title)}"
   ```

4. 因此普通引号可能破坏属性解析；标题本身包含事件载荷、对应事件触发且页面安全策略允许时，进一步具备脚本执行条件。第三方返回的标题应作为数据处理，不应被解释成 HTML 属性结构。

浮动搜索框由 `search-box/search-box.js` 创建。热搜面板最终位于没有 `sandbox` 属性的 `about:blank` iframe 内，继承宿主页面的源；其中执行的页面脚本可以访问同源父页面，并非只影响浮层。这不等于获得普通网页中扩展内容脚本的 `chrome.*` 权限。

### 计划

1. 不再用字符串拼接方式生成热搜链接。
2. 使用 `createElement`、`textContent`、`dataset` 或 `setAttribute` 分别设置文本和属性。
3. 保持当前三项轮播、点击搜索和视觉结构不变。
4. 增加包含双引号、单引号、尖括号及事件属性样式载荷的测试。

实现时应保留每个词条的既有 DOM 契约：元素为 `.trending-word`，当前项带 `.active`，相邻项带 `.adjacent`，`data-offset` 保持数值语义，`data-query`、`title` 和可见文本均来自同一原始标题。不要通过扩充手写转义表继续维持 HTML 模板拼接。

### 测试落点

主要测试文件：

- `tests/search-box/trending-controller.test.js`：控制器级渲染和请求生命周期；
- `tests/search-box/search-box.characterization.test.js`：真实搜索框 iframe 装配及点击行为。

建议在现有“renders three escaped Toutiao trends and opens the active item”场景上补充或新增用例，至少验证：

- 标题 `他说"你好"` 的显示文本、`title` 和 `dataset.query` 完整一致；
- 类似 `" onmouseover="globalThis.__unexpected = true` 的字符串不会产生 `onmouseover` 属性；
- `<img src=x onerror=...>` 只显示为文本，不产生 `img` 元素；
- 点击后发送的 Bing 查询参数来自完整原始标题，而不是被 DOM 解析截断后的值。

### 验收标准

- 任意标题都只能作为文本和属性值存在，不能生成额外元素或额外属性。
- 点击搜索时使用的查询词与接口原始标题一致。
- 正常标题的展示、轮播和点击行为不变。
- 控制器测试与真实搜索框装配测试均须覆盖恶意属性样式字符串；浏览器验证须使用扩展实际创建的 iframe，记录验证环境，不以关闭 CSP 或伪造 DOM 作为功能验收前提。

## 3. 修复官网手机端多出的底部安装引导区

- 将桌面底部安装引导区纳入既有手机端隐藏范围，保留现有手机简介、安装和 GitHub 链接；桌面版该区域照常显示。

## 4. 优化 NTP 当日新壁纸的加载优先顺序

### 保留的行为与优化目标

保留“有缓存先显示旧图，新图可用后再替换”的体验。当天新图尚未进入 IndexedDB 时，需要获取最新目录、取得图片并完成加载；再次打开 NTP 时则可直接使用已缓存的新图。

当前 `wallpaper-page-controller.js` 等待 `displayCached()` 后才调用 `dataSource.refresh()`；`wallpaper-renderer.js` 在旧图 `commit()` 时立即调用 `preload()`，可能先发起 5 张历史图片的网络请求。优化目标是让当天新图获得优先资源，消除不必要的串行等待和历史预加载竞争。没有证据证明这两点解释全部 5–10 秒，但不以进一步测量耗时占比作为实施前置条件，也不承诺固定秒数的提速。

### 加载顺序

1. **并行准备首屏和最新信息。** 确认当前设置允许每日更新、完成本地历史初始化后，即启动 Bing 最新信息请求，同时读取和显示可用的本地图片；不再等旧图加载完成才查询最新信息，也不让网络结果阻塞缓存首屏。
2. **得到新图信息后立即处理目标图片。** 优先复用对应的有效本地缓存；未命中则下载选定画质的新图。下载和加载过程可以与旧图准备并行，不为等待旧图而延后新图请求。同一目标已有进行中的请求时复用，不因两个目录来源先后回调而重复下载。
3. **新图未准备好时保留旧图。** 图片有效且加载完成、当前仍允许每日更新时再提交替换。新图已先准备好则可以直接显示，不强制闪现旧图；旧图迟到的完成事件不得覆盖已经显示的新图。
4. **将随机历史图预加载移出更新过程。** 旧图提交不自动启动随机历史图网络预加载。优先更新已确认无新图、目标图已成功显示或本轮更新已失败结束，并且没有待处理的目标图片后，再于浏览器空闲时恢复可选预加载；保持原有缓存目标数量，按一次一张逐步补充，避免一次并发下载 5 张。不能仅加一个固定延时后继续与尚未完成的新图抢资源，也不能只靠浏览器请求优先级提示代替调度约束。
5. **各目录来源独立推进。** 保留 Bing 与官网索引现有的独立刷新、缓存与合并优先级；Bing 新图无需等待官网索引的请求或超时。官网稍后带来更新候选时走同一目标图片流程，并暂停新增可选预加载。预加载恢复不能简单绑定整个 `Promise.all()` 完成，以免无关来源拖延。

本地图片、当日目标图片、随机历史预加载按上述用途调度，不建立全扩展通用下载队列，不增加后台常驻定时刷新。用户主动选择壁纸、锁定、预览、关闭壁纸或进入空白模式时，继续优先尊重用户操作；过期异步结果不得恢复自动换图或覆盖用户选择。

用户已确认此取舍：优先让当天新壁纸准备就绪，历史随机图随后补齐。当天首次更新期间点击“换一张”，可立即命中的预加载候选可能减少，未缓存的目标可能需要下载；功能本身仍可用。当日更新完成、预加载逐步恢复后，继续保留缓存带来的快捷切换。

### 实施范围

主要涉及 `ntp/modules/wallpaper-page-controller.js`、`wallpaper-data-source.js`、`wallpaper-renderer.js`。协调缓存首屏、最新候选和当前请求的所有权，保留既有请求版本及提交条件检查。新图下载准备不能提前取消尚未完成的缓存首屏；只在目标图准备好后接管显示。不能只把 `refresh()` 提前而不处理旧图迟到覆盖、候选来源交错和重复请求。

保持默认 4K 和用户选择的画质、每日壁纸选择规则、收藏/锁定语义、现有缓存格式不变；不引入低清先显后升清、多级画质下载或新的数据源，也不借此扩展缓存重构。未命中新图缓存才走目标图网络请求；更新失败时继续显示已有旧图，不清空背景。

### 验收标准

在现有 `tests/ntp/wallpaper-page-controller.test.js`、`wallpaper-data-source.test.js`、`wallpaper-renderer.test.js` 及 `tests/e2e/ntp-cache.spec.js` 中补充或调整相关行为覆盖：

原先要求“缓存显示完成后才启动目录刷新”的测试反映的是旧调度，需要改为保护“请求并行且不阻塞缓存首屏”，保留其防止白屏和异步覆盖的行为保障。

- 人为延迟旧缓存图片加载，确认 Bing 信息请求已经启动；人为延迟 Bing，确认旧图可以先正常显示。
- 每日更新与目标图片仍在等待时，不发起随机历史图片网络预加载；无更新、成功和失败路径均能在合适时机恢复可选预加载。
- 新图信息、图片下载、图片加载分别受控时，旧图一直保留，直到新图可提交；新图先完成时不得再被迟到旧图覆盖。
- 官网响应迟缓不阻塞 Bing 图片显示；来源交错不重复请求同一目标，较旧结果不覆盖已选中的更新图片，并保持既有数据合并规则。
- 下载期间锁定、切换收藏、进入预览或空白模式、关闭壁纸时，迟到结果不改变用户选择；再次打开页面仍可使用已缓存的新图。
- 验收聚焦顺序、请求次数与状态正确性，不增加真实网络耗时拆分、长期基准或固定秒数门槛。

## 5. 在 NTP 内部设置增加“显示产品标识”选项

### 需求与当前结构

用户希望长期使用的新标签页能够减少品牌展示。当前 `ntp/ntp.html` 的 `.brand` 独立包含产品图标和“ECHO 易可”文字；普通页面没有单独关闭它的选项。已有空白模式会连搜索框一起隐藏，右上角按钮极简模式只改变操作按钮，二者都不能替代该需求。

这是显示偏好的需求完善，不将目前展示品牌本身定性为 bug。

### 产品行为

- 在 NTP 右上角内部设置面板增加正向开关“显示产品标识”，与热搜、右上角按钮极简模式并列；不加入全局设置页的功能开关列表。
- 默认开启，旧数据中缺少该字段时沿用当前外观。关闭时整体隐藏中央 `.brand` 的图标和文字；重新开启立即恢复。
- 只控制中央品牌区域，保留搜索框、热搜、壁纸、搜索建议、右上角操作和设置入口。不借此修改标签页标题、favicon、页脚文字或设置入口自身的图标。
- 隐藏品牌后按剩余内容重新安排搜索框与热搜的位置，不保留为品牌预留的大块空位。热搜关闭时搜索框在可用内容区域内居中；热搜开启时协调搜索和热搜的整体位置、间距及建议下拉空间。品牌开启时保持既有布局。
- 空白模式继续优先隐藏内容，并按现有规则禁用其它内部设置；退出空白模式后恢复用户此前选择的品牌显示偏好。品牌开关不改变右上角按钮极简模式或壁纸模式。
- 在同一浏览器配置中保存偏好，重新打开 NTP 生效；首屏即应用已保存的隐藏状态，避免先闪现品牌再隐藏。

### 实施落点与数据兼容

1. 在 `ntp/modules/wallpaper-state.js` 增加布尔字段 `showBrand`，默认 `true`，沿用 `echo_ntp_wallpaper_v2` 中现有 NTP 本地偏好存储，不增加 `storage.sync` 全局开关。字段缺失或类型无效按默认显示处理。
2. 在 `ntp/ntp.html` 和 `ntp/modules/wallpaper-settings-controller.js` 增加控件及初始化、保存和失败回滚逻辑；该设置独立于壁纸是否开启，不放进只在壁纸开启时可用的子设置区。
3. 通过 `ntp/ntp.css` 的明确状态样式处理品牌显隐及无品牌布局，覆盖热搜开关、现有高 DPI/矮视口规则；不要仅隐藏图片而留下文字，也不要全局改写品牌开启时的布局。
4. 结合 `ntp/blank-init.js`、`blank-critical.css` 和 `wallpaper-repository.js`，沿用已有首屏偏好预读模式，在样式首次绘制前应用隐藏状态。首屏镜像仅用于及时显示，实际本地设置仍为权威来源；保存、读取校正、失败回滚和备份恢复应保持二者一致。镜像缺失或不可访问时安全回到默认显示，不声称存储不可用时也能保证无闪现。
5. `options/modules/backup-controller.js` 当前导出会包含本地 NTP 设置，但导入的 `WALLPAPER_BACKUP_VALIDATORS` 会丢弃未声明的键。新增 `showBrand` 的布尔验证，使新备份能恢复偏好，旧备份缺字段时保持默认显示，并处理导入后首屏镜像的一致性。这是 NTP 偏好的备份支持，不是在全局设置中新增选项；不调整备份 schema 版本或格式。

### 验收标准

- 默认、旧设置和旧备份保持品牌显示；关闭后中央图标与“ECHO 易可”都不再占据页面空间，搜索和热搜保持可用。
- 开关立即生效，持久保存；保存失败时控件、页面和首屏镜像恢复一致。新备份导入后偏好不丢失，非法字段不能生效。
- 冷启动或新开 NTP 时，已有隐藏偏好在首屏生效；开启/关闭热搜、壁纸及右上角极简模式时布局和设置入口正确；空白模式退出后恢复之前的品牌偏好。
- 在常规与高 DPI/矮视口下验证搜索框、热搜和建议列表不重叠、不越界，品牌开启的旧布局不回归。
- 单元覆盖使用既有设置控制器、状态、存储和备份测试；浏览器覆盖以真实 `ntp.html` 装配验证显隐、布局、重开页面和首屏，不能只用手写 fixture 证明效果。

## 8. 同步隐私与架构文档

### 8.1 补全搜索联想的隐私说明

`ntp/modules/search-controller.js` 在用户输入后约 200ms 防抖发出 `BING_SUGGEST`，`background/network-service.js` 将查询词发送至 `https://api.bing.com/osjson.aspx`，并设置 `credentials: 'omit'`。该请求发生在提交搜索之前。

`PRIVACY_POLICY.md` 当前搜索章节主要解释构造 Bing 搜索 URL 并打开新标签，应同步中英文说明：新标签页搜索联想会将输入的查询词发送给 Bing 获取建议，点击提交则另行打开搜索结果。不得把这一行为描述成所有输入均不离开本地，也不能仅凭联想请求认定开发者收集数据或存在遥测。

本项只准确披露现有行为，不改变搜索功能、不新增开关、不默认关闭联想。可在代码修复前完成；验收时逐句对照实际调用链和接收方，避免作出超出代码证据的数据使用承诺。

### 8.2 更新架构说明

涉及行为变更的说明在相应代码与验证稳定后更新；对现有实现的事实纠错可以独立处理。

### 计划

审计还明确了三项实施约束：壁纸并行调度必须保留缓存首屏与过期结果保护，不能只提前一行调用；品牌设置必须同步备份导入白名单及首屏镜像；未执行的真实浏览器/发布验证不得写成已通过。全部确定任务均有对应代码落点、用户价值和验收条件。剩余真实浏览器边界按本文执行阶段验证，方案审计通过不等于修复完成。

## 执行顺序

1. 标签有序插入状态修复及回归测试；
2. 头条热搜标题解析及属性注入修复、回归测试；
3. 官网手机端底部安装引导区隐藏修复及视口验证；
4. NTP 当日新图优先加载、历史图片预加载后置及行为回归；
5. NTP 内部“显示产品标识”开关、布局与数据兼容及行为回归；
6. 备份导出隐私契约测试；
7. 已确认死代码、失真 fixture 和低价值测试的清理；
8. README、ARCHITECTURE 等中英文文档同步。

搜索联想隐私说明可提前独立完成。其他候选技术债不自动进入上述顺序；用户补充的问题经核实后再纳入本文，并按影响和依赖调整顺序。

后续实施时，每完成一项，先运行与其相关的检查并记录结果，再进入下一项；完成本轮代码修改后统一运行上述完整单元、浏览器集成和发布包校验。
