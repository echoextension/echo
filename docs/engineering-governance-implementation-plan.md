## 1. 文档目的

ECHO 已经发布并拥有真实用户，当前工程治理需要同时解决两类问题：

1. 核心代码中存在体积较大的单体文件、重复实现、状态所有权不清和历史遗留代码；
2. 仓库缺少自动化测试、测试夹具、持续集成和可重复的发布校验，主要依赖人工回归。

本文件用于把后续工作固化为一套可执行、可验收、可追踪的工程计划，并建立实施期间必须遵守的工作契约。

本计划不以“文件越小越好”为目标，也不以覆盖率数字代替真实行为验证。最终目标是：

- 已发布行为得到自动化保护；
- 高风险状态机可以被确定性重放；
- 第三方站点适配具备可维护的契约与失败放行策略；
- 后台和 NTP 的职责边界清晰；
- 每次修改都能说明验证证据、风险和回滚方式；
- 人工 QA 只保留无法稳定自动化的部分。

## 2. 文档权威性与变更规则

### 2.1 权威性

本文件是工程治理工作的顺序基线。实施时不得静默删除阶段、调换高风险阶段顺序或降低阶段门禁。

如需要改变本计划，必须同时记录：

1. 原计划内容；
2. 修改原因；
3. 新证据；
4. 对风险和验收标准的影响；
5. 是否改变用户可见行为或数据兼容性。

### 2.2 代码、运行证据与文档的优先级

结论证据按以下顺序分级：

| 等级 | 证据类型 | 可以支持的结论 |
| --- | --- | --- |
| E1 | 当前提交上的自动化测试或真实浏览器稳定复现 | 可以确认当前缺陷、修复结果或兼容性 |
| E2 | 当前源码和明确的平台语义能够完整推导 | 可以确认代码级或平台级缺陷，但仍需补回归测试 |
| E3 | 当前源码显示风险机制，但结果依赖浏览器、时序或第三方页面 | 只能标记为风险，必须进一步复现 |
| E4 | 历史提交、问题记录、QA 文档或用户旧反馈 | 只能说明历史和预期，不能证明当前缺陷仍存在 |
| E5 | 推测或类比 | 不得进入修复清单，只能转化为待验证假设 |

任何缺陷报告都必须标注证据等级。历史文档中的“阻断”“待修复”或“冒烟失败”不能直接继承到当前 `HEAD`。

### 2.3 完成声明

以下情况不得声明“完成”：

- 测试未实际执行；
- 测试失败后被跳过、删除或用重试掩盖；
- 只完成代码生成，未验证加载和行为；
- 只通过 mock，真实浏览器要求仍未标注；
- 阶段门禁未满足；
- 未核对工作区差异；
- 将“未复现”写成“已修复”。

## 3. 当前系统基线

### 3.1 运行技术栈

ECHO 当前是 Manifest V3、原生 JavaScript/CSS/HTML 的 Chromium/Edge 扩展：

- 主清单：[`manifest.json`](../manifest.json)
- 后台 Service Worker：[`background.js`](../background.js)
- 通用内容脚本：[`content.js`](../content.js)
- 悬浮搜索框：[`search-box/search-box.js`](../search-box/search-box.js)
- 新标签页：[`ntp/ntp.js`](../ntp/ntp.js)
- 设置页：[`options/options.js`](../options/options.js)
- B站视频工具：[`bili-tool/bili-tool.js`](../bili-tool/bili-tool.js)
- B站推荐历史：[`bili-feed-history/bili-feed-history.js`](../bili-feed-history/bili-feed-history.js)
- 知乎黑名单同步与过滤：[`zhihu-tool/zhihu-tool.js`](../zhihu-tool/zhihu-tool.js)
- 扩展页共享交互：[`common/`](../common/)
- 现有人工回归：[`docs/QA-CHECKLIST.md`](./QA-CHECKLIST.md)

当前源码直接作为解压扩展加载，没有生产构建步骤。后续测试工具不得默认改变这一运行方式。

### 3.2 状态层级

后续重构必须明确区分以下状态：

| 状态类型 | 当前示例 | 生命周期要求 |
| --- | --- | --- |
| 同步持久状态 | 通用设置、Bing 壁纸收藏 | 跨设备；受配额和冲突影响 |
| 本机持久状态 | NTP 设置、知乎名单和开关 | 不跨设备；浏览器重启后保留 |
| 浏览器会话状态 | B站按标签页的推荐历史 | 浏览器会话内保留；标签关闭后清理 |
| 页面状态 | DOM、观察器、当前壁纸、当前批次 | 页面销毁后清理 |
| Worker 临时状态 | 标签事件上下文、同步任务运行态 | 不得假设 Service Worker 永久在线 |

任何新增状态都必须声明所属层级，禁止仅因实现方便而放入全局变量。

### 3.3 外部契约

ECHO 依赖以下不受仓库控制的契约：

- Chromium/Edge 扩展 API 和 MV3 Service Worker 生命周期；
- B站页面 DOM、播放器实现和推荐批次行为；
- 知乎页面 DOM、账号状态和黑名单接口；
- Bing、百度、头条及 ECHO 官网壁纸数据接口；
- 下载、DNR、IndexedDB、Canvas 和页面缩放行为。

这些契约必须通过“本地 fixture + 少量浏览器集成 + 人工/定时契约检查”共同保护，不能全部塞入普通单元测试，也不能全部依赖真实外网。

## 4. 总体目标与非目标

### 4.1 总体目标

1. 建立静态校验、单元测试、DOM fixture、Chrome API fake、Chromium 集成测试和 CI；
2. 对当前关键行为建立可执行的特征测试；
3. 先验证、再修复代码和平台证据充分的问题；
4. 统一设置 schema、消息协议和错误结构；
5. 将后台按状态所有权拆分；
6. 将 NTP 按启动、存储、领域逻辑和 UI 生命周期拆分；
7. 统一重复的输入增强策略，保留各页面必要的执行差异；
8. 建立可重复、可审计的发布包生成与验证流程；
9. 收敛人工 QA，使其聚焦真实 Edge 和第三方站点行为。

### 4.2 明确非目标

第一轮工程治理不做以下工作：

- 全面重写扩展；
- 迁移 React、Vue 等 UI 框架；
- 同时迁移 TypeScript 和生产打包系统；
- 仅为缩短行数机械拆分 CSS 或 HTML；
- 将 B站、知乎和通用网页强行合成一个站点框架；
- 使用真实知乎账号或 Cookie 作为公共 CI 条件；
- 使用第三方网站实时可用性阻塞每个 Pull Request；
- 为追求覆盖率测试无业务意义的静态标记或复制生产算法。

## 5. 固定技术决策

### 5.1 测试工具

初始测试体系采用：

- Vitest：测试运行、断言、mock 和 fake timer；
- jsdom：DOM 与事件级测试；
- fake IndexedDB：NTP 缓存和本地数据测试；
- 自研最小 Chrome API fake：标签、窗口、存储、消息、Port、下载和 DNR；
- Playwright 自带 Chromium：后续扩展集成和少量 E2E。

这些依赖均为开发依赖，不进入扩展发布包。

### 5.2 生产模块化方式

初期保持当前经典脚本加载方式，不在拆分后台或 NTP 的同时切换完整模块系统。

模块化要求：

- 使用单一命名空间暴露工厂或纯函数；
- 入口文件负责装配和监听器注册；
- 领域模块不得在加载时隐式注册重复事件；
- 依赖通过参数或明确的模块对象传入；
- 测试调用的必须是生产代码本身；
- 后续是否迁移 ESM 单独决策，不与本轮职责拆分绑定。

### 5.3 覆盖率策略

- 不为现有巨型 UI 文件立即设置全仓覆盖率门槛；
- 新抽取的纯逻辑和状态模块分支覆盖率目标不低于 90%；
- 设置迁移、标签决策、消息校验和快照提交等关键决策模块应达到 100% 分支覆盖；
- 覆盖率不能替代行为矩阵、异常路径和浏览器验证。

后续阶段原则上按顺序推进。阶段 6 实施中确认，NTP 主脚本内的输入适配必须先完成阶段 7 的共享策略，才能满足阶段 6 的薄入口门禁。因此 2026-09-01 记录一次显式依赖调整：先完成阶段 7 的输入策略与 FRE demo 契约，再返回完成阶段 6 的剩余视觉控制器收敛。该调整不删除任何阶段或降低门禁。

## 阶段 0：冻结事实基线

### 0.1 阶段目标

在修改生产代码前，把当前运行面、状态和协议转化为可追踪清单，避免重构过程中丢失隐式契约。

### 0.2 工作内容

1. 记录当前分支、提交、工作树和扩展版本；
2. 解析 `manifest.json` 中的入口、权限、脚本顺序和页面覆盖；
3. 建立设置清单：key、默认值、类型、存储区域、读取方和写入方；
4. 建立消息清单：action、Port、参数、sender、响应和调用方；
5. 建立状态清单：持久、会话、页面和 Worker 临时状态；
6. 建立网络清单：域名、调用位置、数据格式、缓存和失败策略；
7. 将现有 QA 条目映射到实际代码路径，但不把 QA 文档当成当前缺陷证据。

### 0.3 交付物

- 可供测试和审计使用的设置、消息、存储和入口清单；
- 当前行为测试矩阵；
- 需要真实浏览器验证的边界清单。

### 0.4 阶段门禁

- 每个设置和消息均有明确调用方，或被标记为不可达候选；
- 所有存储 key 均有生命周期说明；
- 未修改生产行为；
- 历史文档状态与当前代码事实明确分离。

### 0.5 阶段风险

风险低。主要风险是遗漏动态调用或错误理解隐式协议，通过全仓检索和调用方交叉核对控制。

## 阶段 1：测试基础设施与静态 CI

### 1.1 阶段目标

建立不依赖真实浏览器和第三方网站的快速质量门禁。

### 1.2 工作内容

1. 建立 Node 开发环境和统一测试入口；
2. 建立 jsdom、fake timer 和 fake IndexedDB 基础；
3. 建立有状态的 Chrome API fake；
4. 校验 manifest JSON、权限和资源引用；
5. 校验中英文 locale key；
6. 校验壁纸数据结构、日期、ID 和唯一性；
7. 校验所有生产 JavaScript 可被解析；
8. 建立发布文件 allowlist；
9. 建立 GitHub Actions 快速 CI。

### 1.3 Chrome API fake 最低能力

| API 面 | 必须模拟的行为 |
| --- | --- |
| `runtime` | 消息、异步响应、`lastError`、Port connect/disconnect |
| `storage` | `sync/local/session` 独立数据、变更事件、失败和配额错误 |
| `tabs` | 查询、创建、更新、移动、关闭、缩放、事件顺序 |
| `windows` | 创建、查询、状态更新、关闭和多窗口隔离 |
| `downloads` | 创建任务、完成和中断状态 |
| `declarativeNetRequest` | 动态规则表、冲突、添加、删除和残留 |
| `scripting` | 注入调用记录、成功和失败 |

### 1.4 静态 CI 门禁

- manifest 中声明的文件全部存在；
- locale key 一致；
- 壁纸数据有效；
- JavaScript 语法有效；
- 发布 allowlist 不包含 `crawler` 探针、探针报告或开发材料；
- 权限变化在 CI 输出中可见；
- 快速检查在干净环境可重复执行。

### 1.5 阶段门禁

- CI 能独立运行；
- 所有静态检查通过；
- 测试工具未改变扩展生产加载方式；
- 测试失败能够提供具体文件和原因。

### 1.6 阶段风险

风险低。Chrome fake 只实现实际测试所需能力，禁止一开始模拟整个浏览器。

### 2.3 Fixture 契约

1. fixture 必须最小化，不保存整页 HTML；
2. 删除用户名、ID、Cookie、标题、正文和可识别内容；
3. 每个 fixture 标注来源日期、页面类型和结构假设；
4. 网络 fixture 同时包含成功、空数据、结构变化、429、5xx、超时和乱序；
5. fixture 失败只能证明契约变化，不能自动证明第三方网站整体故障；
6. 生产探针与测试 fixture 可以共享解析规则，但不得将探针扩展打入生产包。

### 2.4 阶段门禁

- 所有核心运行面都有实际测试；
- 测试明确区分当前行为、期望行为和待确认产品语义；
- 失败用例不被隐藏；
- 浏览器特有边界单独列出；
- 大规模生产重构尚未开始。

### 2.5 阶段风险

风险中等。最大风险是假 Chrome API 与真实浏览器语义不一致，因此所有 fake 测试必须注明它能够证明和不能证明的范围。

---

## 阶段 3：验证和修复高价值问题

### 3.0 阶段目标

使用阶段 2 的测试验证审计候选。只有在当前代码或当前浏览器上成立的问题才进入修复。

### 3.1 E2 级候选：优先建立失败测试

以下候选有当前代码或平台语义支持，但仍必须补可执行回归测试：

1. `lastActiveTabId` 可能把已非活动的历史标签误判为刚关闭的活动标签；
2. 全局 `isProcessingRemoval` 会跨窗口抑制标签激活事件；
3. `bossKeyState` 依赖 MV3 Worker 易失内存；
4. 快速存图共用固定 DNR 规则 ID，缺少并发隔离；
5. 壁纸收藏降级写入 local 后没有对应读取路径；
6. 悬浮搜索框隐藏后仍保留动画和缩放轮询；
7. NTP 搜索、热搜和聚焦被壁纸初始化串行阻塞；
8. 搜索建议旧响应可能在新查询之后返回；
9. 壁纸网络响应在缓存前缺少完整的状态、类型和解码验证；
10. 备份导入缺少版本化 schema、字段白名单和事务失败说明。

### 3.2 E3 级候选：必须真实复现

以下内容不得仅凭代码风险或历史文档直接修改：

- 当前知乎页面是否仍会因过滤影响无限滚动；
- 当前知乎同步是否仍会在正常窗口中断连；
- 当前 B站 SPA 导航是否复用 document 并导致推荐历史未重新启动；
- B站新批次“零 URL 重合”条件是否仍适应不同账号和灰度布局；
- 快速滚轮是否在真实浏览器中丢失缩放步进；
- B站视频 DRM、跨源 Canvas、全屏和播放器替换行为；
- Edge 物理快捷键和系统级快捷键冲突；
- 真实防盗链站点的 Referer 要求。

### 3.3 修复规则

1. 先提交失败测试或可重复复现脚本；
2. 记录根因，不以症状命名修改；
3. 使用最小修复，不顺便重构相邻区域；
4. 运行模块测试和相关回归；
5. 记录 mock 通过与真实浏览器通过的差异；
6. 无法稳定复现时保留诊断能力，不猜测修复；
7. 产品语义不明确时停止行为变更，先确定契约。

### 3.4 阶段门禁

- 每个修复都有修复前失败、修复后通过的证据；
- 无关行为没有变化；
- 存储和消息兼容性测试通过；
- 所有阶段 1、2 测试继续通过；
- 未复现风险仍按风险记录，没有伪装成已修复。

### 3.5 阶段风险

风险中到高。标签事件、MV3 生命周期、DNR 和存储冲突必须优先防止“测试环境通过、真实浏览器错误”。

## 阶段 4：统一设置和消息契约

### 4.0 阶段目标

消除默认值漂移、隐式消息参数和无归属 action，为后续拆分建立稳定边界。

### 4.1 设置 schema

唯一 schema 必须包含：

- key；
- 类型；
- 默认值；
- 枚举范围；
- 存储区域；
- 是否设备相关；
- 是否进入备份；
- 旧 key 迁移；
- 非法值修复或拒绝策略。

禁止继续在后台、内容脚本和设置页分别维护完整默认值副本。

### 4.2 消息协议

唯一消息注册表必须包含：

- action 名称；
- 参数结构；
- sender 类型和允许来源；
- URL/域名限制；
- 同步或异步响应；
- 成功和错误结构；
- 超时和取消语义；
- 调用方清单。

### 4.3 清理条件

只有同时满足以下条件，才能删除 action 或遗留代码：

1. 全仓无调用方；
2. manifest 无入口；
3. 运行时无动态字符串引用；
4. 人工 QA 无现行功能依赖；
5. 删除后静态、单元和 smoke 测试通过。

重点审查：

- 重复的 `searchInNewTab`、`openInNewTab`、`getZoom`；
- 已移除 Jieba 后保留的消息分支；
- 无 `bookmarks` 权限的自绘书签遗留；
- 无调用方的壁纸枚举、favicon 和旧状态代码；
- 未注册监听器对应的通知函数。

### 4.4 阶段门禁

- 新增设置只需修改一个 schema；
- 消息参数错误能被明确拒绝；
- action 调用方清单完整；
- 旧用户迁移 fixture 全部通过；
- 删除项均有不可达证据。

### 4.5 阶段风险

风险中等。主要风险是遗漏隐藏调用方和改变旧设置的默认语义，通过调用清单和升级 fixture 控制。

## 阶段 5：拆分后台 Service Worker

### 5.1 阶段目标

让状态所有权、事件输入和浏览器副作用形成明确边界，使 Worker 重启和事件竞态可以单独测试。

### 5.2 目标模块

1. 设置初始化与迁移；
2. 标签插入协调器；
3. 标签关闭状态机；
4. 老板键和静音命令；
5. 消息路由与验证；
6. 图片获取、DNR 和下载；
7. B站 session 协调；
8. 知乎同步任务协调；
9. 后台薄入口。

### 5.3 状态机要求

标签模块使用显式输入和 effect：

- 输入：创建、激活、移动、关闭、附加、分离、窗口创建和窗口关闭；
- 状态：按 `windowId` 隔离；
- 输出：查询、移动、激活、持久化或无操作；
- 不在 reducer 内直接调用 Chrome API；
- 不使用跨窗口全局布尔锁；
- 初始化和事件到达之间需要版本或重放保护。

老板键和知乎任务等跨 Worker 状态必须定义：

- 持久化位置；
- Worker 重启恢复；
- 页面/窗口不存在时的清理；
- 过期任务判定；
- 重复任务拒绝或接管策略。

### 5.4 实施顺序

1. 抽纯决策函数；
2. 抽状态容器；
3. 抽 API effect adapter；
4. 迁移一个监听器；
5. 重放测试；
6. 再迁移下一个监听器；
7. 最后收敛消息入口。

### 5.5 阶段门禁

- `background.js` 只承担装配和启动；
- 一个事件只有一个明确所有者；
- 所有按窗口状态均真正按窗口隔离；
- Worker 重启测试通过；
- 标签矩阵和消息回归全部通过；
- 不再存在无生命周期说明的关键全局状态。

### 5.6 风险与回滚

风险高。每次只迁移一个边界，保留可独立回滚的差异；禁止一次性搬迁整个文件后再补测试。

## 阶段 6：拆分 NTP

### 6.1 阶段目标

解除壁纸、搜索、热搜、存储和页面输入之间的启动耦合，同时保留当前首帧和用户数据行为。

### 6.2 严格拆分顺序

1. 启动编排；
2. 存储 repository；
3. 壁纸数据校验、合并与选择；
4. IndexedDB 图片缓存；
5. 自定义壁纸图像处理；
6. 壁纸状态机；
7. 壁纸 DOM 控制器；
8. 热搜数据源、缓存和状态；
9. NTP 搜索建议；
10. 页面输入适配。

### 6.3 启动编排要求

以下任务不应无理由串行：

- 壁纸数据与图片加载；
- 热搜状态和缓存加载；
- 搜索表单和建议绑定；
- NTP 缩放恢复；
- 输入增强初始化。

首帧镜像仍由轻量同步逻辑负责，网络和 IndexedDB 不得阻塞搜索输入绑定。

### 6.4 存储要求

- 保持既有 key；
- 所有读取均验证类型；
- sync/local 降级有明确的版本和合并策略；
- 自定义壁纸元数据与 Blob 一致性可修复；
- 无效图片缓存可以删除并重新回退；
- localStorage 首帧镜像不是权威数据源；
- 导入备份不能写入任意未知结构。

### 6.5 阶段门禁

- `ntp.js` 只负责页面装配；
- 搜索与热搜不等待壁纸网络；
- 每日、收藏、锁定、关闭和空白模式通过；
- 自定义壁纸和离线缓存通过；
- 旧设置和收藏 fixture 通过；
- 本阶段不同时重构大面积 CSS 或视觉。

### 6.6 风险与回滚

风险高。风险集中在初始化顺序、存储兼容、Blob 生命周期和首帧闪烁。每次拆分必须保留当前存储 key，并对冷启动和缓存启动分别验证。

## 阶段 7：统一输入增强策略

### 7.1 阶段目标

解决普通网页、NTP、设置页、FRE、文档页多套手势、缩放、F2/F3 和拖拽实现的行为漂移。

### 7.2 统一范围

共享：

- 设置门控；
- 缩放步进计算；
- 输入框和可编辑区域判断；
- URL 识别和协议补全；
- 拖拽意图分类；
- 最小拖拽距离；
- 消息格式；
- 右键手势状态转移。

保留各页面差异：

- 普通网页使用浏览器缩放；
- NTP 使用 CSS 缩放；
- 设置页可以提供即时体验；
- FRE 可以显式进入演示模式；
- iframe 只运行被允许的快速存图能力。

### 7.3 必须先确定的产品契约

产品契约已于 2026-09-01 明确：

- 普通网页、NTP、设置页和文档页服从用户的手势、精细缩放、F2/F3 与超级拖拽开关；
- FRE 必须始终保留上述能力的演示，不读取或依赖用户开关；
- FRE 继续显式加载额外演示脚本，并通过 `demo` 模式运行共享能力；
- 用户尚未完成设置、关闭开关或已有关闭状态时，均不得阻止 FRE 演示；
- FRE 的例外只能存在于首次运行演示上下文，不得扩散到其他扩展页面。

### 7.4 阶段门禁

- 同一领域算法只有一个生产实现；
- 页面文件只保留适配层；
- 开关作用范围有测试和文案；
- NTP 专用缩放行为没有被普通网页实现覆盖。

### 7.5 阶段风险

风险中等。主要风险是将原本有意存在的页面差异误判为重复代码。

## 阶段 8：浏览器集成与 E2E

### 8.1 阶段目标

验证单元和 fake 无法证明的扩展上下文、消息、注入和 Worker 生命周期。

### 8.2 自动化范围

使用 Playwright 自带 Chromium 和 persistent context 验证：

- 解压扩展可以加载；
- Service Worker 启动；
- NTP、设置页、FRE 和文档页可打开；
- 本地 HTTP fixture 页面能注入内容脚本；
- 内容脚本与后台通信；
- 标签创建、移动和关闭；
- 主动终止 Worker 后的状态恢复；
- 本地 Referer 测试服务上的 DNR 行为；
- IndexedDB 缓存和离线恢复；
- 关键设置升级路径。

### 8.3 不进入普通 PR 阻塞的项目

- 真实知乎账号与黑名单；
- B站登录态、广告和灰度布局；
- DRM 视频和真实全屏；
- Edge 全局快捷键；
- 真实下载目录和系统权限；
- 外网热搜和壁纸服务的实时稳定性。

### 8.4 Edge 验证策略

Playwright 官方推荐扩展测试使用其自带 Chromium。品牌 Edge 的真实扩展验证继续由人工发布门禁承担，不为了自动化 Edge 侧载而过早引入签名、企业策略或外部安装链。

### 8.5 阶段门禁

- E2E 使用独立浏览器 profile；
- 测试之间不共享标签、存储和 IndexedDB；
- 不使用固定睡眠代替状态等待；
- 不使用无限重试；
- Chromium 结果与 Edge 人工结果分开记录；
- 第三方站点失败不污染扩展本身的 PR 门禁。

### 8.6 阶段风险

风险中等。主要风险是浏览器升级、Worker 重启、窗口焦点和图形环境导致 flaky。只有稳定用例才进入阻塞 CI。

## 阶段 9：CI 与发布流水线

### 9.1 PR 门禁

- 静态资源和数据校验；
- 单元测试；
- DOM fixture；
- Chrome API fake；
- 新模块覆盖率；
- 权限 diff；
- 发布 allowlist 校验。

目标是快速、确定、无外网依赖。

### 9.2 主干门禁

在 PR 门禁基础上增加：

- Chromium 扩展加载 smoke；
- NTP、设置页和内容脚本通信；
- 少量关键标签状态矩阵；
- Worker 重启 smoke。

### 9.3 定时非阻塞任务

- B站公开页面 selector 命中率；
- 知乎公开页面结构契约；
- Bing、百度、头条和远程壁纸 schema；
- 浏览器新版本兼容预警。

定时任务失败产生报告，不自动判断产品代码有缺陷。

### 9.4 发布门禁

- manifest 版本和 CHANGELOG 一致；
- 权限变化已确认；
- 使用 allowlist 生成发布包；
- 发布包不含探针、探针报告、测试和开发文档；
- 发布包可以被 Chromium 加载；
- 产物生成哈希并保存为 CI artifact；
- 完成真实 Edge 人工 QA；
- 商店上传保留人工批准。

### 9.5 阶段门禁

- 同一提交可以重复产生等价发布物；
- CI 失败不能被跳过发布；
- 自动化和人工 QA 责任边界明确；
- 发布流程不依赖开发者记忆选择文件。

## 7. 人工 QA 的收敛方式

现有 [`QA-CHECKLIST.md`](./QA-CHECKLIST.md) 不立即删除。每个条目按以下方式分类：

| 分类 | 处理方式 |
| --- | --- |
| 可由纯逻辑稳定验证 | 转为单元测试后从常规人工清单移除 |
| 可由本地 DOM/API fixture 验证 | 转为 fixture 测试，发布前只抽查 |
| 必须真实浏览器 | 保留 Edge 人工测试 |
| 必须真实第三方站点 | 保留站点狗粮/契约测试 |
| 历史问题且当前无证据 | 移入历史记录，不作为每次发布门禁 |

人工 QA 最终重点保留：

- Edge 物理快捷键；
- 浏览器窗口焦点和真实标签体验；
- 防盗链下载；
- B站播放器、DRM、全屏和灰度布局；
- 知乎登录态、无限滚动和评论变体；
- 高 DPI、页面缩放、深浅主题和视觉质量；
- 商店安装和升级。

## 8. 数据兼容契约

### 8.1 存储 key

任何存储 key 的修改必须提供：

- 旧 key 读取；
- 新 key 写入；
- 幂等迁移；
- 迁移失败回退；
- 已迁移标记或可重复执行证明；
- 全新安装、缺 key、旧类型和损坏值 fixture。

### 8.2 存储区域

- 用户跨设备偏好才允许进入 sync；
- 账号、隐私数据和设备相关状态保留在 local；
- 标签页会话数据保留在 session；
- localStorage 仅用于首帧镜像或页面局部缓存；
- IndexedDB 用于 Blob 和较大本机数据；
- 不允许消费者在不同存储区域自行定义同名 key 的冲突语义。

### 8.3 备份

备份格式必须版本化，并建立：

- 顶层 schema；
- 设置白名单；
- 类型与枚举校验；
- 未知字段处理；
- 旧版本迁移；
- 自定义壁纸排除规则；
- 分步写入失败说明；
- 导入前验证和必要的回滚快照。

---

## 9. 消息与安全契约

所有后台能力必须遵循最小授权：

- 校验 action；
- 校验参数类型和大小；
- 校验 sender；
- URL 必须解析并限制协议；
- 网络代理使用域名和方法白名单；
- B站 session 只能由对应标签上下文访问；
- 图片请求规则精确到请求生命周期；
- 错误响应不暴露隐私数据；
- 未知 action 返回明确错误，不静默成功；
- Port 任务具有 task ID、取消、断开和过期语义。

任何新增 host permission 或扩展权限必须提供功能必要性、替代方案和权限 diff。

---

## 10. 第三方站点契约

### 10.1 通用原则

- 识别失败时放行；
- 不保存整段第三方页面 HTML；
- 不伪造无法可靠恢复的数据；
- 不替换站点核心框架节点；
- 观察器和注入 UI 必须有完整停止路径；
- SPA 导航必须有明确 enter/leave 状态；
- selector 变化产生诊断，不直接隐藏未知内容。

### 10.2 B站

- 卡片解析与渲染通过结构化 schema；
- fixture 覆盖普通、广告和缺字段变体；
- 批次稳定条件由探针数据支持并持续验证；
- 不将单一账号、视口或日期的探针结果永久当作平台保证；
- 视频 Canvas 能力失败时回退，不影响原播放器。

### 10.3 知乎

- 同步只有完整成功才替换快照；
- 账号在同步前后必须一致；
- 取消和失败保留旧快照；
- 作者识别必须基于已验证的稳定标识；
- 无法确认作者时不隐藏；
- DOM 过滤不得破坏信息流加载；
- 真实无限滚动只能由真实页面验证，fixture 不能单独宣称通过。

## 11. 风险分级与控制

| 区域 | 风险 | 主要风险 | 控制方式 |
| --- | --- | --- | --- |
| 静态测试与 CI | 低 | 规则误报 | 小范围规则、明确错误输出 |
| DOM/API fixture | 中 | fake 偏离真实浏览器 | 标注证明边界、补 Chromium 集成 |
| 设置和消息统一 | 中 | 旧数据或隐藏调用方 | 迁移 fixture、全仓调用清单 |
| 后台标签状态机 | 高 | 事件顺序和跨窗口回归 | reducer、事件重放、逐监听器迁移 |
| Worker 状态持久化 | 高 | 过期状态和恢复错误 | task ID、版本、过期和重启测试 |
| NTP 存储和启动 | 高 | 数据丢失、白屏和首帧闪烁 | 保持 key、先数据后 UI、冷/热启动测试 |
| NTP CSS/视觉 | 高、当前收益低 | 层叠顺序改变 | 不与逻辑重构同时进行 |
| B站/知乎适配 | 高波动 | 第三方改版 | fail-open、fixture、定时契约和人工狗粮 |
| 全面框架迁移 | 极高 | 同时改变运行与发布方式 | 当前不实施 |

## 12. 整体完成定义

只有以下条件全部满足，工程治理任务才能宣布完成：

1. 所有主要运行面都有自动化测试；
2. 标签、同步、存储和消息等关键状态机有事件顺序与异常路径覆盖；
3. 新抽取核心模块满足既定分支覆盖率；
4. `background.js` 成为后台薄装配入口；
5. `ntp.js` 成为 NTP 薄装配入口；
6. 设置 schema 只有一个权威来源；
7. 消息 action 只有一个权威注册表；
8. 测试没有生产算法副本；
9. CI 稳定且无隐藏重试；
10. 发布包由 allowlist 生成并可重复验证；
11. 用户数据、旧设置和升级路径受到测试保护；
12. 第三方站点失败遵循放行策略；
13. Chromium 集成测试通过；
14. 真实 Edge 人工发布清单通过；
15. 文档中的当前状态、风险和实际代码一致；
16. 没有把“未执行”“待复现”或“仅 mock 通过”写成完成。

## 13. 工作契约

### 13.1 范围契约

- 本计划覆盖测试、CI、确定缺陷修复、后台拆分、NTP 拆分、输入策略统一和发布治理；
- 不得因执行时间改变而静默缩减范围；
- 如果发现计划缺项，必须补充并说明原因；
- 如果发现某项不应实施，必须用新证据修改计划，而不是直接跳过。

### 13.2 实施契约

- 每个补丁只承担一个明确目标；
- 不大范围格式化无关代码；
- 不顺便修改产品文案或视觉；
- 不覆盖用户未提交改动；
- 不自动 commit、push、合并或发布；
- 修改前读取完整上下文；
- 修改后运行最小相关验证；
- 同一文件连续修复失败达到三次时停止并重新分析，不盲目循环。

### 13.3 验证契约

- 行为变更先有失败测试；
- 纯重构必须证明前后行为等价；
- mock 结果与浏览器结果分开报告；
- Playwright、E2E、构建和完整测试套件在执行前单独说明，并取得当次明确授权；
- 预计超过 30 秒的授权命令，执行前说明预计时长和同步期间无法发送进度；
- 任何失败均保留原始错误和复现条件；
- 不以重试次数掩盖 flaky。

### 13.4 结论契约

- 用户判断、AI 判断和文档记录均需证据验证；
- 不迎合预设结论；
- 不把代码体积直接等同于缺陷；
- 不把静态风险直接写成当前阻断；
- 不把单一探针样本推广成永久平台事实；
- 不把“理论可测”写成“测试已存在”；
- 不报告未经实际执行的通过结果。

### 13.5 阶段报告契约

每个阶段结束必须报告：

1. 本阶段目标；
2. 实际修改文件；
3. 新增或修改的测试；
4. 实际执行的命令；
5. 通过、失败和未执行项；
6. 当前工作树状态；
7. 风险变化；
8. 阶段门禁是否满足；
9. 下一阶段内容；
10. 是否需要新的授权或产品决策。

推荐报告格式：

```text
阶段：
状态：完成 / 未完成 / 阻塞
生产变更：
测试变更：
已执行验证：
结果：
未执行项：
风险：
门禁结论：
下一步：
```

### 13.6 异常与停止条件

遇到以下情况时停止相关区域，保留其他可独立工作：

- 工作树出现来源不明的外部改动；
- 发现可能破坏用户数据但缺少迁移方案；
- 产品语义冲突且无法从当前实现和文案确定；
- 真实浏览器行为与 fake 模型矛盾；
- 第三方测试需要账号、Token、Cookie 或其他秘密；
- 命令要求管理员权限或交互式输入秘密；
- 阶段门禁失败且继续会放大变更范围。

停止时必须说明具体阻塞，不得将阻塞改写为范围外事项。
